## 1. 协议层修正

### 1.1 接收帧校验和应使用低 5 位

**证据**：用真实抓包 62 帧验证（`comm_latest.txt`）

| 算法 | 匹配率 |
| --- | --- |
| `sum(b[2..18]) & 0xFF` | 18/62 = **29%** |
| `sum(b[2..18]) & 0x1F` | 62/62 = **100%** |

实例：帧 `... 29 d5 19`，`sum = 729`，`729 & 0xFF = 0xD9 ≠ 0x19`，但 `729 & 0x1F = 0x19` ✓

**当前实现状态**：`lib/core/protocol.dart` 的 `parseNotify()` **完全不校验接收帧**（只判断 `d.length >= 13 && d[0] == 0xAC`）。
全工程仅 `frame()` 在发送时写入 `p[19] = sum & 0xFF` —— 这是**安全**的，因为秤只比低 5 位。

**要做什么**：
- 若将来给 `parseNotify` 增加完整性校验，**必须**写成 `(sum & 0x1F) == (d[19] & 0x1F)`
- `b[19]` 高 3 位不是校验数据，不能参与比对

⚠️ **按 8 位校验会丢掉 71% 的帧，App 会表现为"连上了但一帧数据都收不到"。**

### 1.2 收到历史帧（0xD8 / b[2]=0x01）应立即回 ACK

**证据**：真实日志 10 个历史帧只包含 **6 条唯一记录**

```
ts=1795010111 → 出现 3 次
ts=1795015308 → 出现 3 次
```

**原因**：秤每 1.5 秒重发未被确认的记录。当前实现在握手末尾（t+2400ms / t+2800ms）固定发两条 `04 D8`，
那时秤已经重发过 2~3 遍。`addPending` 的去重掩盖了症状，但流量与秤的行为都不对。

**要做什么**：
- 每收到一条 `b[2] == 0x01` 的历史帧，**立即**发送 `04 D8`（`operate_type=4, reply_cmd=0xD8`）
- 握手序列里的两条固定 `04D8` 可以保留（无害）或删除
- 顺带：`04 D6` 与 `04 D8` 的 `b[18]` 都是 `0xDF`、`b[2]` 都是 `0x04`，仅 `b[3]` 区分（`0xD6`/`0xD8`）

**量级评估**：

| 历史积压 | 推送帧数 | 耗时（120ms/帧）|
| --- | --- | --- |
| 1~3 条（日常）| 3~9 | < 1.2s |
| 30 条 | ~80 | 9.6s |
| 100 条 | ~270 | 32s（接近秤 45~70s 断开上限）|

数据不会丢（未 ACK 的下次仍会推），只是重复与变慢。

### 1.3 解析 `b[18]` 命令字与 `b[19]` 高 3 位单位

**现状**：只按 `d[2]` 分包类型，未使用 `b[18]` 与 `b[19]` 高 3 位。

**命令字（`b[18]`）与包类型（`b[2]`）的对应关系**（真实日志实测一一对应）：

| `b[2]` | `b[18]` | 含义 |
| --- | --- | --- |
| `0x00` | `0xD5` | 实时/稳定体重帧 |
| `0x02` | `0xD6` | 锁定帧（含阻抗）|
| `0x01` | `0xD8` | 历史帧 |
| `0x06` | `0xDF` | 配置块 |

→ 当前固件上两者冗余，但用 `b[18]` 判定更符合协议语义（`b[2]` 是载荷首字节，语义上属于 payload）。

**单位位（`b[19] & 0xE0 >> 5`）**：`0 = kg` / `1 = lb` / `2 = st` / `3 = 斤`
- 实测 46 个接收帧**全部为 0（kg）**，因为 App 每次连接都在 `D0` 帧里写 `unit = 0x00`
- 若用户在秤上手动改单位，体重解析会错（把 lb 当 kg → 差 2.2 倍）
- **建议**：解析时读取该字段，非 0 时按对应单位换算或直接告警

## 2. 体成分算法校准（已用真实数据完整反推，未实施）

### 2.1 男性算法：14 项指标可 100% 复现官方 App

**样本**（爱月 2026-11-19 提供，蚂蚁 App 与本地 App 逐项对照）：

```
身高 168cm · 体重 79.95kg · 出生 2002-10-03（24 岁）· 男
阻抗1 = 386Ω · 阻抗2 = 348Ω · 合成 = 495.45Ω
```

**反推结论**：官方男性算法的旧系数有 4 处偏差 + 1 处舍入策略差异。按下表修改后可 14/14 全项命中。

| 项 | 当前实现 | 官方实际 | 说明 |
| --- | --- | --- | --- |
| 男性偏移量 | `- 11.22` | **`- 11.25`** | 体脂率 25.46% → 官方显示 25.4% |
| 骨量% | `4.5%` | **`3.8774%`** | 79.95kg → 3.1kg |
| 蛋白质% | `16.3%` | **`15.7598%`** | 79.95kg → 12.6kg |
| 水分系数 | `0.7185` | **`0.7252`** | 乘以去脂体重 |
| 骨骼肌系数 | `0.548` | **`0.5545`** | 乘以肌肉% |
| 皮下脂肪系数 | `0.7165` | `0.7165` | ✓ 无需修改 |

**舍入策略**（关键，也是当前所有 0.1 差异的来源）：

```
官方口径：每一个"率"都四舍五入到 1 位，然后用该率去算"量"
当前实现：只在最终输出时四舍五入，中间值保留全精度
```

正确顺序：

```
体脂率     = round(1.10×BMI + 0.23×年龄 − 11.25, 1)      ← 先定这个
脂肪量     = round(体重 × 体脂率/100, 1)
去脂体重   = round(体重 − 体重×体脂率/100, 1)            ← 用未舍入的脂肪量算
骨量       = round(体重 × 3.8774%, 1)
肌肉率     = round(100 − 体脂率 − 3.8774, 1)
肌肉量     = round(肌肉率 × 体重/100, 1)
骨骼肌率   = round(肌肉率 × 0.5545, 1)
骨骼肌量   = round(骨骼肌率 × 体重/100, 1)
水分率     = round((100 − 体脂率) × 0.7252, 1)
水分量     = round(水分率 × 体重/100, 1)
蛋白质量   = round(体重 × 15.7598%, 1)
皮下脂肪率 = round(体脂率 × 0.7165, 1)
皮下脂肪量 = round(皮下脂肪率 × 体重/100, 1)
基础代谢   = round(370 + 21.6 × 去脂体重)
```

**验证结果（改前 → 改后）**：

| 指标 | 当前实现 | 修改后 | 官方 |
| --- | --- | --- | --- |
| 体脂率 | 25.5% | 25.4% | 25.4% ✓ |
| 脂肪量 | 20.4 kg | 20.3 kg | 20.3 kg ✓ |
| 去脂体重 | 59.6 kg | 59.6 kg | 59.6 kg ✓ |
| 肌肉量 | 56.0 kg | 56.5 kg | 56.5 kg ✓ |
| 肌肉率 | 70.0% | 70.7% | 70.7% ✓ |
| 骨骼肌量 | 30.7 kg | 31.3 kg | 31.3 kg ✓ |
| 骨骼肌率 | 38.4% | 39.2% | 39.2% ✓ |
| 蛋白质量 | 13.0 kg | 12.6 kg | 12.6 kg ✓ |
| 骨量 | 3.6 kg | 3.1 kg | 3.1 kg ✓ |
| 水分率 | 53.6% | 54.1% | 54.1% ✓ |
| 水分量 | 42.8 kg | 43.3 kg | 43.3 kg ✓ |
| 皮下脂肪率 | 18.2% | 18.2% | 18.2% ✓ |
| 皮下脂肪量 | 14.6 kg | 14.6 kg | 14.6 kg ✓ |
| 基础代谢 | 未实现 | 1658 kcal | 1658 kcal ✓ |

**改哪些文件**：`lib/core/bodycomp.dart`（系数与舍入）、`lib/core/models.dart`（BodyComposition 增加 bmr 字段）、UI 增加 BMR 显示。

**注意**：`docs/ALGORITHM.md` 里把男性公式标成「Deurenberg 1991 原式（✅ 原式）」是**错误标注**——
论文原式是 `1.20×BMI + 0.23×年龄 − 10.8×性别 − 5.4`（男性展开为 `−16.2`），我们的系数与之不同，属于**校准变体**。
实施校准时应同步修正该文档（6 语言）。

### 2.2 男性「不用阻抗」的验证状态

**当前实现**：男性分支完全不读取阻抗（`bf = 1.10×BMI + 0.23×年龄 − 11.22`）。

**证据**：同一体重下把阻抗从 0 拉到 1200Ω，9 项指标**全部不变**。

**但这只是逆向结果，不是生理规律**：
- Segal 1988 论文为男性也提供了阻抗方程（本次未取得其精确系数）
- 官方 APK 里 `ICAlgorithmManager.calc()` 直接 `return d`（空壳），算法在服务端 → 本地是对服务端输出的复刻

**待验证（低成本）**：

```
① 空腹赤脚称重 → 记录官方体脂率 X1、本 App 阻抗 R1
② 喝 500ml 水等 20 分钟
③ 再称 → 记录 X2、R2（体重约 +0.5kg，阻抗降 30~50Ω）
判读：X2 ≈ X1 + 0.1pp → 官方不用阻抗；X2 降 1~2pp → 官方用了阻抗
```

## 3. 待新增指标

### 3.1 基础代谢 BMR（公式已破解）

```
BMR = 370 + 21.6 × 去脂体重     ← Katch-McArdle 公式，单位 kcal
```

**验证**：79.95kg / 25.4% → 去脂体重 59.64kg → `370 + 21.6×59.64 = 1658.3` → 官方显示 **1658 kcal** ✓

对照排除：

| 公式 | 结果 | 是否命中 |
| --- | --- | --- |
| Mifflin-St Jeor | 1734.5 | ✗ 差 76 |
| Harris-Benedict | 1829.4 | ✗ 差 171 |
| **Katch-McArdle** | **1658.3** | ✓ |
| Cunningham | 1812.1 | ✗ 差 154 |

**实现要点**：BMR 只依赖去脂体重（而男性去脂体重来自不含阻抗的公式），所以**男性 BMR 同样不受阻抗影响**。

### 3.2 内脏脂肪等级（算法未知）

官方 App 显示「内脏脂肪等级 10」，当前实现无此指标。

- 常见做法是 `VFR` 与腰围 / 阻抗 / 体脂率相关，但官方具体公式未知
- **需要**：多组官方显示值 + 对应体重/阻抗/体脂率，才能反推（至少 4~5 组）

### 3.3 其他可推算指标（官方未显示，可选）

| 指标 | 公式 | 是否官方有 |
| --- | --- | --- |
| TDEE | `BMR × 活动系数`（1.2 久坐 / 1.375 轻 / 1.55 中）| 否（是假设不是测量）|
| FFMI | `去脂体重 / 身高(m)²`，归一化 `+ 6.1×(1.8 − 身高)` | 否 |
| FMI | `脂肪量 / 身高(m)²` | 否 |
| 目标体重 | `去脂体重 / (1 − 目标体脂率)` | 部分场景 |

## 4. 待验证的协议假设

### 4.1 时间帧的时间字段字节序

**分歧**：

| 来源 | 说法 | 我们的实现 |
| --- | --- | --- |
| 外部逆向（OpenAfu）| 小端 int32（`ICStreamBuffer.WriteInt` 小端）| — |
| 本实现 | 大端（`nowSec >> 24, >> 16, >> 8, nowSec`）| 发出去的是大端 |

**观测**：真实日志里我们发的是 `ac 27 08 6a fd d0 b7 e0 ...`，按大端解 = 1794973879（合理时间）；按小端解 = 3083599210（2030 年，不合理）。

**为什么目前没出问题**：秤的历史帧时间戳来自秤自己的 RTC（实测历史帧时间为正确的 2026-11-18），不依赖我们发的时间帧。

**待验证**：把时间帧改成小端发一次，观察历史记录时间戳是否变化。若不变 → 该字段对秤无实际作用，维持现状即可。

### 4.2 ServiceData 是否包含真实 MAC

**分歧**：

| 来源 | 说法 |
| --- | --- |
| 本实现（nRF Connect 实测）| ServiceData = 6 字节 MAC **倒序** + `01`，解出设备真实 MAC |
| 外部逆向（OpenAfu）| ServiceData 只有 7 字节协议标识/版本/状态，**不含 MAC**，用 BLE 地址即可 |

**状态**：我们的解析在当前设备上工作正常（连接成功）。但对方文档该处样本为合成值，无法直接比对。

**待验证**：用 nRF Connect 抓一条真实广播，逐字节核对 ServiceData 是否确实等于 MAC 倒序。

### 4.3 `fun_open_imp` 配置位的语义

**外部发现**：用户信息帧里的 `flags` 字节 bit0 = `fun_open_imp`（体脂测量总开关）。被写成 0 后秤只报体重、阻抗恒为 `[0,0]`，看起来像硬件故障；写回 1 即恢复。

**我们的现状**：`D0` 完整握手帧的 `p[14] = 0x03`（bit0 + bit1），**已包含 bit0 = 1**，所以功能上是开着的。但代码里没有语义注释，不知道这个字节的含义。

**建议**：补注释说明 `p[14]` 是 flags 位图（bit0 阻抗开关 / bit1 小体重模式 / bit4 婴儿模式），避免将来误改成 0。

### 4.4 广播持续时间

| 来源 | 说法 |
| --- | --- |
| 本实现实测 | 999ms 间隔持续广播，未亮屏也在广播 |
| 外部逆向 | 只在被踩醒后约 2~3 分钟内广播，测完即停 |

**差异可能来自**：观测时段不同（踩醒后 vs 休眠后）。实际使用中"连不上"多为秤已休眠，属正常现象。

## 5. 已知局限（无法修复，只能标注说明）

### 5.1 体脂算法可能来自服务端

外部逆向发现：蚂蚁 APK 里 `ICAlgorithmManager.calc()` 是空壳（`return d`），算法疑在服务端。

**含义**：本地的 14/14 复刻是「对服务端输出的拟合」。若服务端更换算法，本地公式会立即失准，需要重新采集样本反推。

**建议**：在 App 的「关于」或详情页注明「体成分为本地公式估算，与官方 App 存在小幅差异」。

### 5.2 蛋白质与骨量是纯体重的换算

```
骨量     = 体重 × 3.8774%
蛋白质量 = 体重 × 15.7598%
```

这两项**只随体重变化**，与体脂率无关，信息量为 0（是体重换算器）。与官方一致，但不应被当作独立测量。

**建议**：UI 上标注为「推算值」。

### 5.3 增重时「肌肉量」会上涨（公式假象）

男性固定身高年龄、只改体重：

| 体重 | 体脂率 | 肌肉量 | 水分量 |
| --- | --- | --- | --- |
| 65kg | 19.6% | 49.3kg | 37.5kg |
| 85kg | 27.4% | **57.9kg** | **44.3kg** |

体重 +20kg，公式给出肌肉 +8.6kg、水分 +6.8kg —— 明显不合理。
根因是 `肌肉% = 100 − 体脂% − 骨量%`，体脂% 涨得比体重慢，相乘后绝对值反而上升。

### 5.4 单点数据无法拟合阻抗模型

若要让男性也用阻抗，公式形式为 `BF = a·H² + b·Z + c·W + d`，**4 个未知数**。
一组数据只能给出 1 个方程 → 无穷多组解。至少需要 4 组「体重相近、阻抗不同」的样本。

### 7.2 判定「是否使用阻抗」（需 4 组以上）

同一人、相近体重、**不同水合状态**下反复测量，记录：

| 序号 | 体重 | 阻抗1 | 阻抗2 | 官方体脂率 | 备注 |
| --- | --- | --- | --- | --- | --- |
| 1 | | | | | 空腹晨起 |
| 2 | | | | | 饮水后 20 分钟 |
| 3 | | | | | 运动后 |
| 4 | | | | | 洗澡后 |

有了这张表，就能判断官方体脂率是否随阻抗变化，并据此决定是否值得实现「阻抗版男性公式」。
