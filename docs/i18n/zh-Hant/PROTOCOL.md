## 0. 一句話概括我們在做什麼

這台秤本質是一台**會說話的電子秤**。它和手機之間：

1. 秤不停地在空氣裡「廣播」自己的名字和身分（像店鋪掛著招牌）
2. 手機收到招牌後連上去，拿到兩個「信箱」：一個用來發，一個用來收
3. 手機按固定順序塞進去 8 封格式統一的小紙條（**握手**）
4. 秤開始往收信箱裡丟資料包，手機逐位元組拆開、算出體重和體脂

聽起來簡單，但**每一層都有坑**——常見協議文件只寫「應該怎麼做」，
這篇把「實際做的時候會怎麼翻車」也寫進去了。

---

## 1. 先認識幾個詞

藍牙裡有一堆術語，第一次看會懵。用**快遞櫃**打個比方：

| 術語 | 快遞櫃類比 | 實際含義 |
| --- | --- | --- |
| **廣播（Advertising）** | 櫃子上貼的招租廣告 | 裝置不用連線，也能一直往外喊「我在這，我叫什麼」 |
| **掃描（Scan）** | 物業拿著地圖挨個看廣告 | 手機不連線，只「聽」空氣裡誰在喊 |
| **GATT** | 快遞櫃的整套管理制度 | 藍牙低功耗（BLE）傳資料的標準規則集 |
| **服務（Service）** | 一個櫃子，比如「3 號櫃」 | 一組功能的集合，用 UUID 編號 |
| **特徵值（Characteristic）** | 櫃子裡的一個小格子 | 真正存/取資料的地方，也有自己的 UUID |
| **寫入（Write）** | 你往裡塞快遞 | 手機 → 裝置 發資料 |
| **通知（Notify）** | 櫃子滿了主動推送微信提醒 | 裝置 → 手機 主動發資料（不用手機問）|
| **UUID** | 櫃子的編號，如 `0000ffb0-...` | 一串 128 位元（16 位元組）的編號，標識某個服務/格子 |
| **MAC 位址** | 身分證號 | 藍牙裝置唯一的硬體位址，如 `B0:82:AB:07:76:24` |
| **位元組序（大端/小端）** | 數字 1234 是「1 先寫還是 4 先寫」 | 多個位元組拼一個數字時，高位在前還是低位在前 |

**為什麼要知道位元組序**：後面你會發現，同樣是體重，秤在兩種封包裡一個用**大端**一個用**小端**，
搞反了就會算出離譜的數字（比如把 55.75kg 讀成 14 噸）。

## 2. 第一步：在空氣裡找到它（掃描）

### 2.1 秤都「喊」了什麼

秤的廣播裡帶著這幾樣東西（我們用 nRF Connect 和系統日誌核對過）：

| 內容 | 值 |
| --- | --- |
| 廣播名 | `AFU-WL-TZ-A1` |
| 服務 UUID | `0xFFB0`、`0x1530` |
| 廠商資料 | 廠商 ID `0x27AC` |
| **ServiceData** | `0x27AC` + **真實 MAC（6 位元組，倒序）+ 01** |
| 廣播間隔 | 999 毫秒 |

**這裡有個反直覺的點**：廣播裡出現的那個藍牙位址（RemoteID），
**不一定是秤真實的 MAC**。真實值藏在 ServiceData 裡，而且是**倒著放的**。

```
ServiceData 原始位元組： 24 76 07 AB 82 B0 01
                         └──── 6 位元組倒序 ────┘ └(固定 01)
倒過來讀：               B0:82:AB:07:76:24   ← 這才是真 MAC
```

> 我們第一次解析時看漏了「倒序」，結果 MAC 差了一位，怎麼也連不上。[WT/實測]

### 2.2 手機怎麼認出它

三個條件**任意命中一個**就算：

1. 廣播名裡含 `AFU-WL`
2. ServiceData 裡的 UUID 是 `0x27AC`
3. 廣播的服務列表含 `0xFFB0`

### 2.3 兩個必須知道的坑

**坑一：不要用 UUID 做前置過濾**

很多教學教你 `startScan([ffb0 的 UUID])`，只掃帶這個服務的裝置——在這台秤上**會漏**。
實測 MIUI 上這樣做 4 分鐘都掃不到；改成「全掃 + 在回呼裡自己篩」，1 秒出結果。[實測]

**坑二：別加 `neverForLocation` 標誌**

Android 12 以後申請藍牙掃描權限時，如果帶上「這個掃描不用於定位」的標誌，
系統會**靜默過濾掉**某些型別的廣播（這台秤的廣播正好被判定成 beacon）。
現象是：權限都給了、藍牙也開了，就是掃不到。

logcat 裡能看到：`Skipping data matching denylist`。去掉這個標誌就好。[實測]

## 3. 第二步：連上去，拿到兩個「信箱」

連線用第 2 步解出來的**真實 MAC**。連上之後，你會看到一個服務：

```
服務 0000ffb0-0000-1000-8000-00805f9b34fb
  ├── 特徵值 FFB1  ← 手機往這裡「寫」命令
  └── 特徵值 FFB2  ← 秤往這裡「發」資料（需要先訂閱通知）
```

### 3.1 寫信箱 FFB1：只能寄「掛號信」

BLE 寫入有兩種模式：

| 模式 | 通俗解釋 | 這台秤支援嗎 |
| --- | --- | --- |
| **WRITE**（帶回應） | 掛號信，會告訴你「收到了」 | ✅ 必須用這個 |
| WRITE_NO_RESPONSE（不帶回應） | 往門縫裡塞紙條，不管收沒收到 | ❌ **100% 報錯** |

> 這是最容易卡住的地方：某些 BLE 程式庫預設用「不帶回應」模式（效能更好），
> 在這台秤上每次都會拋出異常。我們用 8 次寫入驗證過，全都失敗。[實測]

### 3.2 收信箱 FFB2：要先「訂閱」

手機不能乾等著秤發資料，得先呼叫一次 `setNotifyValue(true)`（訂閱）。
訂閱之後，秤每發一條，手機的「回呼函式」就會被呼叫一次，參數是 20 個位元組。

```dart
// flutter_blue_plus 的做法
await char.setNotifyValue(true);
char.onValueReceived.listen((data) {
  // data 是 Uint8List，長度 20
});
```

### 3.3 順便能讀到的裝置資訊

秤還暴露了一個標準資訊服務 `0x180A`（Device Information），能讀到：

| 欄位 | 值 |
| --- | --- |
| 製造商 | ICOMON |
| 型號 | FG2313UWB-D |
| 韌體版本 | 1.2.3 |
| 軟體版本 | 1.3.0 |

⚠️ **別去讀電量特徵值 `0x2A19`**——這台秤根本沒有這個標準服務，
讀出來的是垃圾值（比如 77%），真電量藏在資料包裡的另一個位置（見 §6.3）。[實測]

## 4. 第三步：搞懂「信封」的格式

手機和秤之間所有訊息都是**固定 20 位元組**，一個位元組不多一個位元組不少。
你可以把它想成一個標準的信封，上面印著幾個固定的格子：

```
位元組位置：[0]  [1]   [2] [3] [4] ... [17]   [18]   [19]
          ┌────┬────┬──────────────────────┬──────┬──────┐
內容：    │ AC │類型│      正    文          │ 尾部 │ 校驗 │
          │    │    │     （16 位元組）      │(命令)│ 和   │
          └────┴────┴──────────────────────┴──────┴──────┘
```

| 位置 | 叫什麼 | 說明 |
| --- | --- | --- |
| `[0]` | 起始標誌 | 固定 `0xAC`，相當於信封上的「航空郵件」戳 |
| `[1]` | 裝置類型 | 手機發 `0x27`，秤回 `0x29`（雙方各報各的「身分」）|
| `[2..17]` | 正文 | 16 位元組，真正的命令和資料放這裡 |
| `[18]` | 尾部 | 命令編號，幫助區分這是哪個命令 |
| `[19]` | 校驗和 | 防止傳輸過程中資料被改壞 |

### 4.1 校驗和是什麼

想像你寄一封信，在信封封口處寫一個數字：**「裡面所有字的筆畫數加起來」**。
收信人拆開後重新數一遍，如果對不上，說明信在路上被弄壞了。

這裡的規則是：

```
校驗和 = (第2到第18位元組全部相加) & 0xFF
```

**`& 0xFF` 是什麼意思**？

一個位元組最大能存 255。相加的結果可能遠超 255（比如 2000），
`& 0xFF` 就是「**只保留最後 8 個二進位位元**」，等價於「對 256 取餘數」。

```
舉例：相加得到 2000
2000 = 二進位 11111010000   （11 位）
只看後 8 位 → 11010000 = 208
所以校驗和寫 208（0xD0）
```

> ⚠️ 注意範圍是 `[2..18]`——**包含尾部 `[18]`，不包含自己 `[19]`**。
> 網路上有文件說「只對正文求和」，照做會一直失敗。[實測逐位元組核對]

### 4.2 正文超過 16 位元組會被砍掉

拼幀函式裡有個截斷：第 2 到第 17 共 16 格，多出來的直接丟棄。
所以**單條命令的正文最多 16 位元組**，塞不下就得分包。

## 5. 第四步：按順序發 8 條命令（握手）

連上之後**不能直接問資料**，得先「報到」。秤要先認識你是誰，才肯幹活。

順序固定，每條間隔 **400 毫秒**（發太快對方處理不過來會丟）。

| # | 命令 | 作用 | 正文（16 位元組）|
| --- | --- | --- | --- |
| 1 | `08` 對時 | 告訴秤「現在幾點」 | `08` + Unix 秒（4 位元組）+ 時區 |
| 2 | `01` 使用者 | 告訴秤「我是誰」 | `01 00 01` + 身高 + 體重（2 位元組×100）+ 年齡 + 性別 |
| 3 | `02` 槽位 | 覆蓋秤裡存的使用者設定 | 兩組各 7 位元組（槽位1 / 槽位2）|
| 4 | `D0` 完整握手 | 一次性把所有資訊再報一遍 | 時間 + 時區 + 單位 + 槽位 + 身高 + 體重 + 年齡 + 性別 + 目標 + `03 00` |
| 5 | `06` 查詢 | 問設定 | `06` |
| 6 | `04 D6` | 提高即時封包頻率 | `04 D6` |
| 7 | `04 D8` | 請求歷史記錄（第一次）| `04 D8` |
| 8 | `04 D8` | 請求歷史記錄（第二次）| `04 D8` |

### 5.1 幾個容易搞錯的細節

**① 時區怎麼算**

```
utcQuarters = (UTC 偏移分鐘數 ÷ 15) & 0xFF
```

為什麼按 15 分鐘？因為世界上有些時區是 UTC+5:30、UTC+5:45 這種半小時/一刻鐘的偏移，
用 15 分鐘當最小單位剛好能表示全部時區。中國是 UTC+8 → 480 分鐘 → 480÷15 = **32**。

**② 性別只有兩個值**

```
男 = 1    女 = 2
```

⚠️ 這不是程式設計裡常見的「0/1」，是**1 和 2**。寫錯會導致體脂公式選錯，結果差一倍。

**③ 體重要乘 100 儲存**

體重用 2 個位元組（最大 65535）儲存，單位是「百分之一公斤」。
所以 55.75kg 存成 `5575` = 十六進位 `0x16 0b`。

**④ 身高只存整數**

身高只佔 1 個位元組（最大 255cm），所以 168.6cm 會變成 **168**。

**⑤ 這些數值從哪來**

```
體重 = 成員檔案裡的體重 → 最近一次測量記錄 → 都沒有的話就用 60kg 兜底
目標體重 = 使用者設定的 → 沒設定就用「參考體重 × 0.75」
```

### 5.2 第 3 條 `02` 命令的特殊性

官方的螞蟻 App **只在「解除綁定裝置」時**發這條命令，作用是清掉秤裡存的使用者槽位。

我們改成**每次連線都發**——因為遇到過秤裡殘留舊設定（身高卡在 111cm，怎麼都改不掉），
重發這條能覆蓋掉。屬於實驗性做法，副作用見 §8。[HCI]

## 6. 第五步：讀懂秤回的話

秤發來的封包也是 20 位元組，`[0]` 是 `0xAC` 但 `[1]` 變成 `0x29`。
真正的「這是哪種封包」藏在 `[2]` 裡：

| `[2]` 的值 | 封包型別 | 什麼時候出現 |
| --- | --- | --- |
| `0x00` | 即時封包 | 測量過程中，每 100~150ms 一條 |
| `0x80` | 穩定封包 | 體重穩定下來了 |
| `0x02` | **鎖定封包** | 測量完成，帶最終阻抗（最重要）|
| `0x01` | 歷史封包 | 連線後秤主動推未同步的舊記錄 |
| `0x06` | 設定區塊 | 應答 `06` 查詢，連推 5 包 |

### 6.1 體重怎麼從 3 個位元組算出來

這是全篇最需要理解的地方。先看即時封包用的公式（**小端式寫法**）：

```
體重(g) = ((d[3] - 0x68) × 65536 + d[4] × 256 + d[5]) ÷ 1000
```

**為什麼要乘 65536 和 256？**

因為一個位元組只能存 0~255，存不下幾百公斤（以公克為單位是幾十萬）。
所以用了**三個位元組拼成一個「大數字」**：

```
把三個位元組想像成三個旋鈕：
  第 1 個旋鈕（d[3]）：每轉一格 = +65536
  第 2 個旋鈕（d[4]）：每轉一格 = +256
  第 3 個旋鈕（d[5]）：每轉一格 = +1

這就像十進位裡：百位 ×100、十位 ×10、個位 ×1
只不過這三個「位」是 256 進位，所以權重是 65536 / 256 / 1
```

**`- 0x68` 是幹什麼的？**

秤的出廠「零點」不是 0，而是 `0x68`（十進位 104）。相當於老式體重計的指針本來就沒對準零，
要先扣掉這個偏移量。

**`÷ 1000`**：因為算出來的單位是公克，要換成公斤。

### 6.2 鎖定封包的體重為什麼換了位置和寫法

鎖定封包的體重在 **`d[10..12]`**（不是 `d[3..5]`），而且公式變成了：

```
體重(g) = ((d[10]<<16 | d[11]<<8 | d[12]) - 0x680000) ÷ 1000
```

**`<<16`、`|` 是什麼？**

`<<16` 就是「左移 16 位」，等價於 **× 65536**；`|` 是「把三段拼起來」。
所以這個公式和上面本質是**同一個演算法**，只是寫法更「程式設計師」：

```
寫法 A（小學生版）       寫法 B（位元運算版）
d[10] × 65536            d[10] << 16
d[11] × 256              d[11] << 8
d[12] × 1                d[12]
三者相加                 三者用 | 拼起來
```

⚠️ 但**偏移量不同**：這裡是 `0x680000`（不是 `0x68`）。
因為數字整體放大了 65536 倍，偏移也要跟著放大。

**完整實例**（這是我們實機上抓到的一條）：

```
原始封包：ac 29 02 00 01 ae 01 83 01 80 68 d9 c6 ...
                             └──┬──┘
                             體重三位元組

d[10]=0x68  d[11]=0xD9  d[12]=0xC6
拼起來：0x68d9c6 = 6,871,494
減去偏移：6,871,494 - 0x680000(6,815,744) = 55,750
除以 1000：55,750 ÷ 1000 = 55.75

→ 體重 55.75 kg ✅

同一封包裡的阻抗：
阻抗1 = (d[4]<<8 | d[5]) = (0x01<<8 | 0xae) = 256 + 174 = 430 Ω
阻抗2 = (d[6]<<8 | d[7]) = (0x01<<8 | 0x83) = 256 + 131 = 387 Ω
```

### 6.3 電量藏在哪

**沒有標準電池服務**（§3.3 說過）。真電量在即時封包的 `d[11]` 的**低 7 位**：

```
電量 = d[11] & 0x7F
```

`& 0x7F` = 「只保留低 7 位」（最高位當作標誌位，不算進電量）。

⚠️ **兩個陷阱**：
1. 測量過程中 `d[11]` 會變成 `0x64`（=100），這是「測量完成」的狀態標誌，**不是電量**，要排除
2. 這台秤的電量長期就顯示 **10%** 左右（915 條擷取封包的眾數），不是壞了

### 6.4 歷史封包（`0x01`）

連線成功後秤會自動把所有「沒同步過」的舊記錄推下來，每條也是 20 位元組：

```
時間   = d[3..6]   （Unix 時間戳，4 位元組，大端）
體重   = ((d[8]<<16 | d[9]<<8 | d[10]) - 0x680000) / 1000
阻抗1  = (d[11]<<8 | d[12])
阻抗2  = (d[13]<<8 | d[14])
```

**觸發條件**（這點很關鍵）：

```
寫完「08 對時 + 01 使用者 + D0 完整握手」之後，秤會自動把所有未同步記錄推下來，
04D8 不是必需的（發了更保險）。
```

推完之後，秤在內部把這些記錄標記成「已同步」，**以後不再推**，直到產生新的測量。
如果秤裡本來就沒有記錄，連線後會一片安靜——這是正常的，不是壞了。

⚠️ **同一個時間戳可能收到 3 次**（藍牙會重複投遞），必須去重。
我們的做法是用 `時間戳_體重` 拼成唯一 key 判斷。

### 6.5 怎麼判斷「現在測到哪一步了」

```
收到 0x02                          → 完成（有最終阻抗）
收到 0x00 或 0x80，且 d[11] >= 100 → 正在測阻抗
其他                                → 正在秤重
```

**關於阻抗最重要的一句**：

> 阻抗只由**物理條件**決定。雙腳赤腳踩住四個電極片形成人體迴路才有值；
> 單腳、穿襪子、腳底太乾，阻抗一定是 **0**，任何命令都變不出來的。[A/B 對照實測]
>
> 網路上說「發 `04 D6` 就能開啟阻抗測量」是**錯的**——那只讓即時封包變多（26→77 條）。
> 真正的阻抗數值只出現在 `0x02` 鎖定封包的第 4~8 位元組。

## 7. 一次完整測量，從頭到尾是什麼樣

```
時間軸
│
├─ 使用者踩上秤，秤螢幕亮起
│
├─ 秤：廣播裡喊「我是 AFU-WL-TZ-A1」        —— 999ms 一次，不停喊
│
├─ 手機：掃到它 → 按 MAC 連線 → 訂閱 FFB2
│
├─ 手機：按順序發 8 條命令（每條隔 400ms）   —— 約 3.2 秒
│    08 對時 → 01 使用者 → 02 槽位 → D0 握手
│    → 06 查詢 → 04D6 → 04D8 → 04D8
│
├─ 秤：開始推 0x00 即時封包（每 100~150ms）     —— 數字在跳
├─ 秤：體重穩定 → 推 0x80 穩定封包
├─ 秤：進入阻抗測量 → d[11] >= 100
├─ 秤：測量完成 → 循環推 0x02 鎖定封包（約 6 秒）—— 帶最終阻抗
│
├─ 手機：解析鎖定封包 → 算出體重 + 體脂 → 存庫
│
├─ 秤：如果還有沒同步的舊記錄 → 推 0x01 歷史封包
│         推完在秤內部標記「已同步」
│
└─ 結束（秤過一會兒自己休眠）
```

**為什麼鎖定封包要循環推 6 秒**？因為藍牙可能丟包，多推幾次保證手機一定收到。
手機只要收到一次就可以停了。

## 8. 我們真的踩過的坑

這一節是本文件最有價值的部分——**網路上四份逆向文件都沒提到**。

### 坑 1 · 寫特徵值只能用「掛號信」模式

`FFB1` 只支援帶回應的寫入。用不帶回應模式，**100% 拋出異常**。
（vitaloop 用 Kotlin 預設就是帶回應，所以沒踩到；某些 JS/Dart 程式庫預設不帶。）

### 坑 2 · Android 12 的「denylist」會靜默吃掉廣播

掃描權限帶 `neverForLocation` 標誌時，這台秤的廣播被系統判定為 beacon 並過濾掉。
權限全給了、藍牙也開著，就是掃不到，logcat 裡只有一句 `Skipping data matching denylist`。

### 坑 3 · MIUI 上不同藍牙程式庫速度差 400 倍

同一支手機、同一台秤：

| 程式庫 | 掃描耗時 |
| --- | --- |
| `flutter_blue_plus` | **1 秒內** |
| `react-native-ble-plx` | **約 7 分鐘** |

這是**程式庫的封裝層差異**，跟權限無關。這也是我們最終從 RN 改寫成 Flutter 的直接原因。

### 坑 4 · 用 UUID 做掃描過濾會漏掉秤

`startScan([ffb0 的 UUID])` 在 MIUI 上 4 分鐘無結果；全量掃描 + 回呼裡自己篩，秒出。

### 坑 5 · 剛連上時狀態會「假斷開」

GATT 建立的那一瞬間，連線狀態會短暫誤報 `disconnected`。
如果直接掛個「斷開就重連」的計時器，就會**握手兩遍**——秤會當成新的同步工作階段，把歷史重推一遍。

修法：重連前先複查 `isConnected`，並加一個「正在連線中」的並發鎖。

### 坑 6 · 判斷「體重變了沒」的閾值不能太大

我們想把最新體重回填到成員檔案，需要判斷「值有沒有變」。

| 閾值 | 後果 |
| --- | --- |
| 1 kg | 漲了 0.1kg 視為「沒變」，永遠不更新 |
| 0.05 kg | 浮點數精度問題：55.85 − 55.80 算出來是 0.0499…，還是被擋 |
| **0.001 kg** | ✅ 最終採用 |

### 坑 7 · 男女要用完全不同的體脂公式

```
男性 = Deurenberg 公式：1.10×BMI + 0.23×年齡 − 11.22   （阻抗不參與！）
女性 = Segal 公式：需要阻抗，把兩組阻抗合成 (i1+i2)×0.675
```

**還有一個要知道的**：秤自己螢幕上顯示的體脂率，和 App 算出來的**會差零點幾個百分點**。
因為秤用的是廠商私有演算法（不公開），App 用的是上面這些公開論文裡的公式。

兩者**BMI 永遠一致**（BMI 只看體重和身高，沒有演算法分歧的地方）。

套錯性別，結果差將近一倍。舉個例子（55.75kg / 163cm / 24歲 / 阻抗 430+387）：

| 用哪個公式 | 算出的體脂率 |
| --- | --- |
| 男性公式 | 17.4% |
| 女性公式 | 22.2% |

### 坑 8 · 秤裡存著「上一次的使用者設定」

秤會保留上次寫入的使用者槽位。如果 App 裡的檔案改了但秤裡還是舊的，
秤屏顯示的體脂會明顯不對。這也是我們每次連線都發 `02` 命令覆蓋的原因。

### 坑 9 · 電量不是 77%，是 10%

| 來源 | 讀數 | 真偽 |
| --- | --- | --- |
| 標準電池服務 `0x2A19` | 77% | ❌ 垃圾值（這服務根本不存在）|
| 即時封包 `d[11] & 0x7F` | 10% | ✅ 真值（915 條擷取封包眾數）|

### 坑 10 · 秤沒有「刪除記錄」這個功能

官方 29 條寫命令我們全查過了，**沒有任何刪除/清空指令**。

這意味著：一旦秤把某條記錄標記成「已同步」，任何 App 都拿不到它了。
**App 漏存 = 永久遺失**。所以連線期間千萬別中途殺行程。

## 9. 和網路上四份逆向文件的差異

我們參考了五個開源專案，但**照著做會翻車**的地方不少。
這節列的是實測結論與文件說法的出入，方便後來者少走冤枉路。

### 9.1 文件說法 vs 實測結論

| # | 文件怎麼說 | 實測是什麼 | 證據 |
| --- | --- | --- | --- |
| 1 | [AF] 體重是完整 32 位，用 `& 0x3FFFF` 分檔 | 即時/穩定封包用 `((d[3]-0x68)×65536+d[4]×256+d[5])/1000`；**鎖定封包體重在 d[10:13]**，兩處位置不同 | 55.75kg 全鏈路核對 |
| 2 | [AF] 秤休眠時不廣播，必須踩亮 | 本秤**未亮屏也在廣播**（999ms），nRF 2 秒掃到，驗證台 84ms | nRF + 通訊日誌 |
| 3 | [AF] 資料包每 15 秒重發，需要心跳 | **心跳非必需**，不發也能穩定出阻抗 | 無心跳實測正常 |
| 4 | [VA] 握手時 weight/target 填 0 | 填**真實值**更好，秤內槽位與檔案一致 | 實測日誌 |
| 5 | [VA] 只發一條 `D0` 握手就夠 | 不帶 `01` 使用者命令時**阻抗不觸發**，8 條全序列最穩 | 前後對比 |
| 6 | [WT] ServiceData 的 payload 帶 `AC27` 前綴 | payload = **MAC 6 位元組（倒序）+ 01**，沒有前綴 | 原始位元組核對 |
| 7 | [WT] `D6` 命令是阻抗來源 | `D6` 只讓即時封包變多（26→77 條），**最終阻抗在 `0x02` 包 d[4:8]** | A/B 對照 |
| 8 | [WT/HCI] 校驗和 = 正文求和 | 精確為 **`sum(frame[2..18]) & 0xFF`**（**含尾部 [18]**）| 逐位元組核對 |

### 9.2 四份文件都沒寫、我們自己發現的

1. `FFB1` **只支援帶回應寫入**（詳見坑 1）
2. Android 12 的 `neverForLocation` 會導致廣播被 denylist 過濾（坑 2）
3. MIUI 上兩種藍牙程式庫速度差 400 倍（坑 3）
4. UUID 前置過濾會漏秤（坑 4）
5. 連線瞬間狀態抖動會導致雙握手（坑 5）
6. 檔案回填閾值必須小到 0.001kg（坑 6）
7. 男女 BIA 公式完全不同（坑 7）
8. `02` 命令的真實語意是「寫兩組使用者槽位，每組 7 位元組」
9. 電量真值在 `d[11]` 低 7 位，且這秤沒有 `0x2A19` 服務（坑 9）
10. 「已同步」標記對**任何** App 都生效，加上沒有刪除命令 = 漏存即永久遺失（坑 10）

### 9.3 和官方螞蟻 App 的有意差異

| 官方怎麼做 | 我們怎麼做 | 為什麼 |
| --- | --- | --- |
| 只在解綁時發 `02` | 每次連線都發（實驗性）| 覆蓋秤裡殘留的舊使用者設定（曾卡在 111cm）|
| 每 15 秒重發資料包（心跳）| 不發 | 實測非必需，省電 |
| `04D8` 發一次 | 發兩次 | 保險，沒觀察到副作用 |
| iOS 用戶端 | Android / Flutter | 掃描策略不同（見坑 3、坑 4）|

### 9.4 還沒驗證的問題

- [ ] 每次連線都發 `02` 的長期副作用（如果發現歷史被反覆重推，改回「僅解綁時發」）
- [ ] `deviceType` 發 `0x29` 是否在部分韌體上必需（vitaloop 用 0x29 也能工作）
- [ ] 體脂率與秤屏那 0.4 個百分點差異是否隨體重恆定
- [ ] 15 秒心跳在超長連線（>10 分鐘）下是否必要

## 10. 自己怎麼偵錯

### 10.1 開啟 App 裡的通訊日誌

日誌入口預設藏著（彩蛋）：

> **設定 → 關於 → 連點版本號 7 次**

解鎖後測量頁右上角出現「通訊 N」按鈕，能看到每一條收發的原始位元組。

### 10.2 日誌檔案自動落盤

連線期間每 3 秒寫一次（斷開時再強制寫一次）：

```
/storage/emulated/0/Android/data/com.aiyue.afu_scale/files/comm_latest.txt
```

```bash
adb pull /storage/emulated/0/Android/data/com.aiyue.afu_scale/files/comm_latest.txt
```

格式：`时间 方向(→发出 / ←收到) 原始20字节 [命令名或包类型]`

### 10.3 系統層面的關鍵字

| 現象 | logcat 關鍵字 |
| --- | --- |
| 掃描被系統過濾 | `Skipping data matching denylist` |
| 掃描過程打點 | `SCAN_STEP` |
| 寫入失敗 | `PlatformException` + `not supported` |

### 10.4 用 nRF Connect 交叉驗證

自己寫的程式行為詭異時，先用 **nRF Connect**（手機上的通用 BLE 偵錯工具）手動連一次，
看能不能正常收到資料。如果 nRF 也不行，說明是物理/環境問題（沒踩亮、離太遠、電量低）。

## 附：給「想自己實作」的人一張速查表

```
1. 掃描：全量掃，回呼裡按「名字含 AFU-WL / ServiceData 是 27AC / 服務含 FFB0」篩
2. 取 MAC：ServiceData 裡 6 位元組倒序
3. 連線 → 拿到服務 FFB0
4. 訂閱 FFB2 的通知（setNotifyValue(true)）
5. 往 FFB1 寫 8 條命令，每條隔 400ms，全部用「帶回應」模式
6. 聽 FFB2 的回呼，按 [2] 判斷封包型別
7. 0x02 封包：體重在 d[10:13]，阻抗在 d[4:8]，都要減偏移再除 1000
8. 收到 0x02 就完事了，存庫
```

**最容易翻車的三處**：寫入模式（必須帶回應）、校驗和範圍（含 [18]）、體重偏移量（`0x68` vs `0x680000`）。
