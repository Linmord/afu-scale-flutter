## 0. 何をしているのかを一行で

この秤は本質的に**しゃべる電子秤**だ。秤とスマホの間では：

1. 秤は空中に自分の名前と身元を絶えず「アドバタイジング」している（店先に看板を掲げるように）
2. スマホは看板を受け取ると接続し、2 つの「私書箱」を手に入れる。1 つは送信用、1 つは受信用
3. スマホは決まった順序で、書式の揃った 8 通のメモを差し込む（**ハンドシェイク**）
4. 秤は受信箱にデータパケットを投げ込み始め、スマホはバイト単位で解きほぐして体重と体脂肪を算出する

聞くと簡単だが、**各層に落とし穴がある**——よくあるプロトコル文書は「こうするべき」しか書かないが、
この記事は「実際にやるとどこで事故るか」まで書き込んでいる。

## 1. まず用語をいくつか

Bluetooth には用語が山ほどあり、初見では戸惑う。**宅配ロッカー**に例えてみよう：

| 用語 | 宅配ロッカーの類比 | 実際の意味 |
| --- | --- | --- |
| **アドバタイジング（Advertising）** | ロッカーに貼られた入居者募集の広告 | 接続しなくても、ずっと外に向かって「ここにいる、名前はこれ」と叫べる |
| **スキャン（Scan）** | 管理人が地図を持って広告を 1 つずつ見て回る | スマホは接続せず、空中で誰が叫んでいるかだけを「聞く」 |
| **GATT** | 宅配ロッカーの管理制度一式 | Bluetooth Low Energy（BLE）でデータを送る標準ルールセット |
| **サービス（Service）** | 1 つのボックス、たとえば「3 番ボックス」 | 機能のまとまりで、UUID で番号付けされる |
| **キャラクタリスティック（Characteristic）** | ボックスの中の小さな仕切り | 実際にデータを保存／取得する場所で、独自の UUID を持つ |
| **書き込み（Write）** | 自分で荷物を放り込む | スマホ → デバイス へデータを送る |
| **通知（Notify）** | ロッカーが満杯になると自発的にプッシュ通知を送る | デバイス → スマホ へ能動的にデータを送る（スマホが聞かなくてよい）|
| **UUID** | ボックスの番号、例 `0000ffb0-...` | 128 ビット（16 バイト）の番号で、あるサービス／仕切りを識別する |
| **MAC アドレス** | 本人確認書類の番号 | Bluetooth デバイス固有のハードウェアアドレス、例 `AA:BB:CC:DD:EE:FF` |
| **バイトオーダー（ビッグエンディアン／リトルエンディアン）** | 数値 1234 を「1 から書くか 4 から書くか」 | 複数バイトで 1 つの数値を作るとき、上位バイトが先か下位バイトが先か |

**なぜバイトオーダーを知る必要があるか**：この先わかるが、同じ体重でも秤は 2 種類のパケットで片方は**ビッグエンディアン**、片方は**リトルエンディアン**を使う。
逆にするととんでもない数値になる（55.75kg を 14 トンと読むなど）。

## 2. ステップ 1：空中で見つける（スキャン）

### 2.1 秤は何を「叫んで」いるか

秤のアドバタイジングには次のものが載っている（nRF Connect とシステムログで照合済み）：

| 内容 | 値 |
| --- | --- |
| アドバタイジング名 | `AFU-WL-TZ-A1` |
| サービス UUID | `0xFFB0`、`0x1530` |
| メーカーデータ | メーカー ID `0x27AC` |
| **ServiceData** | `0x27AC` + **実 MAC（6 バイト、逆順）+ 01** |
| アドバタイジング間隔 | 999 ミリ秒 |

**ここに直感に反する点がある**：アドバタイジングに現れる Bluetooth アドレス（RemoteID）は、
**秤の本当の MAC とは限らない**。真の値は ServiceData の中に隠れていて、しかも**逆順に置かれている**。

```
ServiceData 生バイト：  FF EE DD CC BB AA 01
                        └─── 6B 逆順 ───┘  └(固定 01)
逆から読む：            AA:BB:CC:DD:EE:FF   ← これが本当の MAC
```

> 最初に解析したとき「逆順」を見落とし、MAC が 1 桁ずれて、どうやっても接続できなかった。[WT/実測]

### 2.2 スマホはどう見分けるか

3 つの条件の**どれか 1 つ**を満たせば該当とみなす：

1. アドバタイジング名に `AFU-WL` を含む
2. ServiceData の UUID が `0x27AC`
3. アドバタイジングのサービス一覧に `0xFFB0` を含む

### 2.3 必ず知っておくべき 2 つの落とし穴

**落とし穴 1：UUID で事前フィルタしない**

多くのチュートリアルは `startScan([ffb0 の UUID])` と教え、このサービスを持つ機器だけをスキャンする——この秤では**取りこぼす**。
実測では MIUI でこうすると 4 分経っても見つからない。「全スキャン + コールバック内で自分で絞る」に変えたら 1 秒で結果が出た。[実測]

**落とし穴 2：`neverForLocation` フラグを付けない**

Android 12 以降で Bluetooth スキャン権限を要求するとき、「このスキャンは位置情報に使わない」というフラグを付けると、
システムは特定の種類のアドバタイジングを**黙ってフィルタする**（この秤のアドバタイジングがちょうど beacon と判定される）。
症状は、権限を全部与え、Bluetooth も有効なのに、スキャンできないこと。

logcat には `Skipping data matching denylist` が見える。このフラグを外せば直る。[実測]

## 3. ステップ 2：接続して 2 つの「私書箱」を手に入れる

接続にはステップ 2 で解いた**真の MAC** を使う。接続すると、1 つのサービスが見える：

```
サービス 0000ffb0-0000-1000-8000-00805f9b34fb
  ├── キャラクタリスティック FFB1  ← スマホはここにコマンドを「書き込む」
  └── キャラクタリスティック FFB2  ← 秤はここにデータを「送る」（先に通知を購読する必要あり）
```

### 3.1 送信箱 FFB1：送れるのは「書留」だけ

BLE の書き込みには 2 つのモードがある：

| モード | 平易な説明 | この秤は対応するか |
| --- | --- | --- |
| **WRITE**（応答付き） | 書留。受け取ったと教えてくれる | ✅ これを必ず使う |
| WRITE_NO_RESPONSE（応答なし） | ドアの隙間にメモを突っ込むだけ。届いたかは問わない | ❌ **100% エラーになる** |

> ここが最も詰まりやすい箇所だ。一部の BLE ライブラリは既定で「応答なし」モードを使う（性能が良いため）。
> この秤では毎回例外が投げられる。書き込み 8 回で検証し、すべて失敗した。[実測]

### 3.2 受信箱 FFB2：まず「購読」が必要

スマホは秤がデータを送ってくるのを待つだけではだめで、まず `setNotifyValue(true)`（購読）を 1 回呼ぶ。
購読後は秤が 1 件送るたびにスマホの「コールバック関数」が 1 回呼ばれ、引数は 20 バイトになる。

```dart
// flutter_blue_plus でのやり方
await char.setNotifyValue(true);
char.onValueReceived.listen((data) {
  // data は Uint8List、長さ 20
});
```

### 3.3 ついでに読めるデバイス情報

秤は標準情報サービス `0x180A`（Device Information）も公開していて、次が読める：

| フィールド | 値 |
| --- | --- |
| メーカー | ICOMON |
| 型番 | FG2313UWB-D |
| ファームウェア版 | 1.2.3 |
| ソフトウェア版 | 1.3.0 |

⚠️ **バッテリーのキャラクタリスティック `0x2A19` を読んではいけない**——この秤にはこの標準サービスがそもそも無く、
読めるのはゴミ値（たとえば 77%）で、真の残量はデータパケットの別の位置に隠れている（§6.3 参照）。[実測]

## 4. ステップ 3：「封筒」の書式を理解する

スマホと秤の間のすべてのメッセージは**固定 20 バイト**で、1 バイトも増えず減らない。
いくつかの固定枠が印刷された標準的な封筒だと考えればよい：

```
          [0]    [1]           [2] … [17]            [18]         [19]     
         ┌──────┬──────┬──────────────────────────┬───────────┬─────────────┐
         │  AC  │  型  │    本文（16 バイト）     │   尾部    │  チェック   │
         │      │      │                          │(コマンド) │    サム     │
         └──────┴──────┴──────────────────────────┴───────────┴─────────────┘
```

| 位置 | 名称 | 説明 |
| --- | --- | --- |
| `[0]` | 開始フラグ | 固定 `0xAC`。封筒でいう「航空郵便」のスタンプ |
| `[1]` | デバイスタイプ | スマホは `0x27` を送り、秤は `0x29` を返す（双方がそれぞれの「身元」を名乗る）|
| `[2..17]` | 本文 | 16 バイト。実際のコマンドとデータはここに入る |
| `[18]` | 尾部 | コマンド番号。どのコマンドかを区別する助けになる |
| `[19]` | チェックサム | 転送中にデータが壊れるのを防ぐ |

### 4.1 チェックサムとは

手紙を出すとして、封筒の封をする部分に数字を 1 つ書く：**「中のすべての文字の画数を合計した値」**。
受け取った人が開けて数え直し、合わなければ途中で壊れたということだ。

ここでのルールは：

```
チェックサム = (第 2 から第 18 バイトまでを全部加算) & 0xFF
```

**`& 0xFF` とは何か**？

1 バイトが格納できる最大は 255。加算結果は 255 を大きく超えうる（たとえば 2000）。
`& 0xFF` は「**最後の 8 ビットだけを残す**」ことで、「256 で割った余り」と等価だ。

```
例：加算結果が 2000
2000 = 2 進数 11111010000   （11 ビット）
下位 8 ビットだけ見る → 11010000 = 208
よってチェックサムは 208（0xD0）
```

> ⚠️ 範囲が `[2..18]` である点に注意——**尾部 `[18]` を含み、自分自身 `[19]` は含まない**。
> ネット上には「本文だけを合計する」と書いた文書があり、その通りにすると必ず失敗する。[実測バイト単位照合]

### 4.2 本文が 16 バイトを超えると切り捨てられる

フレーム組み立て関数には切り捨て処理があり、第 2 から第 17 までの 16 枠に入りきらない分はそのまま破棄される。
したがって**1 コマンドの本文は最大 16 バイト**で、入りきらなければ分割するしかない。

## 5. ステップ 4：8 つのコマンドを順に送る（ハンドシェイク）

接続後**いきなりデータを聞くことはできない**。まず「名乗り」が必要だ。秤は相手が誰かを知らないと動いてくれない。

順序は固定で、各コマンドの間隔は **400 ミリ秒**（速く送りすぎると相手が処理しきれず取りこぼす）。

| # | コマンド | 役割 | 本文（16 バイト）|
| --- | --- | --- | --- |
| 1 | `08` 時刻合わせ | 秤に「今何時か」を伝える | `08` + Unix 秒（4 バイト）+ タイムゾーン |
| 2 | `01` ユーザー | 秤に「自分が誰か」を伝える | `01 00 01` + 身長 + 体重（2 バイト×100）+ 年齢 + 性別 |
| 3 | `02` スロット | 秤に保存されたユーザー設定を上書き | 2 組×7 バイト（スロット 1 / スロット 2）|
| 4 | `D0` 完全ハンドシェイク | すべての情報をまとめて 1 回で名乗る | 時刻 + タイムゾーン + 単位 + スロット + 身長 + 体重 + 年齢 + 性別 + 目標 + `03 00` |
| 5 | `06` 照会 | 設定を問い合わせる | `06` |
| 6 | `04 D6` | リアルタイムパケットの頻度を上げる | `04 D6` |
| 7 | `04 D8` | 履歴記録を要求（1 回目）| `04 D8` |
| 8 | `04 D8` | 履歴記録を要求（2 回目）| `04 D8` |

### 5.1 間違えやすい細部

**① タイムゾーンの計算**

```
utcQuarters = (UTC オフセットの分数 ÷ 15) & 0xFF
```

なぜ 15 分単位か。世界には UTC+5:30、UTC+5:45 のような 30 分／15 分刻みのオフセットを持つタイムゾーンがあり、
15 分を最小単位にすればすべてのタイムゾーンを表現できるからだ。中国は UTC+8 → 480 分 → 480÷15 = **32**。

**② 性別は 2 値だけ**

```
男性 = 1    女性 = 2
```

⚠️ プログラミングでよくある「0/1」ではなく、**1 と 2** だ。誤ると体脂肪の計算式の選択を誤り、結果が 1 倍近く違ってくる。

**③ 体重は 100 倍して保存**

体重は 2 バイト（最大 65535）で保存し、単位は「100 分の 1 キログラム」。
したがって 55.75kg は `5575` = 16 進で `0x16 0b` と格納される。

**④ 身長は整数のみ**

身長は 1 バイト（最大 255cm）しかないので、165.4cm は **165** になる。

**⑤ これらの値の出どころ**

```
体重 = メンバープロフィールの体重 → 直近 1 回の測定記録 → どちらも無ければ 60kg でフォールバック
目標体重 = ユーザー設定値 → 未設定なら「参照体重 × 0.75」
```

### 5.2 3 番目の `02` コマンドの特殊性

公式の Ant Afu アプリは**「デバイスの紐付け解除」時だけ**このコマンドを送る。役割は秤に保存されたユーザースロットを消すことだ。

私たちは**接続のたびに送る**ように変えた——秤に古い設定が残る事例に遭遇したからだ（身長が 111cm に張り付いて、どうしても直せなかった）。
送り直せば上書きできる。実験的な扱いで、副作用は §8 を参照。[HCI]

## 6. ステップ 5：秤の返事を読み解く

秤から来るパケットも 20 バイトで、`[0]` は `0xAC` だが `[1]` が `0x29` に変わる。
本当の「これはどの種類のパケットか」は `[2]` に隠れている：

| `[2]` の値 | パケット種別 | いつ現れるか |
| --- | --- | --- |
| `0x00` | リアルタイムパケット | 測定中、100〜150ms ごとに 1 件 |
| `0x80` | 安定パケット | 体重が安定した |
| `0x02` | **確定パケット** | 測定完了、確定インピーダンス付き（最重要）|
| `0x01` | 履歴パケット | 接続後、秤が未同期の旧記録を自発的に送る |
| `0x06` | 設定ブロック | `06` 照会への応答、5 パケット連続で送る |

### 6.1 体重を 3 バイトからどう算出するか

ここがこの記事で最も理解が必要な箇所だ。まずリアルタイムパケットの式を見る（**リトルエンディアン形式の書き方**）：

```
体重(g) = ((d[3] - 0x68) × 65536 + d[4] × 256 + d[5]) ÷ 1000
```

**なぜ 65536 と 256 を掛けるのか？**

1 バイトは 0〜255 しか格納できず、数百キロ（グラム単位なら数十万）は入らない。
そこで**3 バイトを 1 つの「大きな数」に組み合わせている**：

```
3 つのバイトを 3 つのつまみだと考えよう：
  1 つ目のつまみ（d[3]）：1 目盛り回すごとに +65536
  2 つ目のつまみ（d[4]）：1 目盛り回すごとに +256
  3 つ目のつまみ（d[5]）：1 目盛り回すごとに +1

これは 10 進数でいう 100 の位 ×100、10 の位 ×10、1 の位 ×1 と同じ
ただしこの 3 つの「位」は 256 進数なので、重みは 65536 / 256 / 1 になる
```

**`- 0x68` は何のためか？**

秤の出荷時の「ゼロ点」は 0 ではなく `0x68`（10 進で 104）。昔の体重計の針がもともとゼロに合っていないのと同じで、
先にこのオフセットを引く必要がある。

**`÷ 1000`**：計算結果の単位がグラムなので、キログラムに直すため。

### 6.2 確定パケットでは体重の位置も書き方も変わるのはなぜか

確定パケットの体重は **`d[10..12]`** にあり（`d[3..5]` ではない）、しかも式がこう変わる：

```
体重(g) = ((d[10]<<16 | d[11]<<8 | d[12]) - 0x680000) ÷ 1000
```

**`<<16` や `|` とは何か？**

`<<16` は「16 ビット左シフト」で、**× 65536** と等価。`|` は「3 つの部分を連結する」。
したがってこの式と上の式は本質的に**同じアルゴリズム**で、書き方がより「プログラマ的」なだけだ：

```
書き方 A（小学生版）      書き方 B（ビット演算版）
d[10] × 65536            d[10] << 16
d[11] × 256              d[11] << 8
d[12] × 1                d[12]
3 つを足す               3 つを | で連結
```

⚠️ ただし**オフセットが違う**：ここは `0x680000`（`0x68` ではない）。
数値全体が 65536 倍に拡大されているので、オフセットも同じだけ拡大させる必要がある。

**完全な実例**（実機で捕まえた 1 件）：

```
生パケット：ac 29 02 00 01 ae 01 83 01 80 68 d9 c6 ...
                                          └──┬───┘
                                       体重 3 バイト

d[10]=0x68  d[11]=0xD9  d[12]=0xC6
連結：0x68d9c6 = 6,871,494
オフセットを引く：6,871,494 - 0x680000(6,815,744) = 55,750
1000 で割る：55,750 ÷ 1000 = 55.75

→ 体重 55.75 kg ✅

同じパケットのインピーダンス：
インピーダンス1 = (d[4]<<8 | d[5]) = (0x01<<8 | 0xae) = 256 + 174 = 430 Ω
インピーダンス2 = (d[6]<<8 | d[7]) = (0x01<<8 | 0x83) = 256 + 131 = 387 Ω
```

### 6.3 バッテリー残量はどこに隠れているか

**標準のバッテリーサービスは無い**（§3.3 で述べた）。真の残量はリアルタイムパケットの `d[11]` の**下位 7 ビット**にある：

```
バッテリー残量 = d[11] & 0x7F
```

`& 0x7F` = 「下位 7 ビットだけを残す」（最上位ビットはフラグとして扱い、残量には数えない）。

⚠️ **2 つの罠**：
1. 測定中に `d[11]` が `0x64`（=100）になることがあるが、これは「測定完了」の状態フラグで**残量ではない**。除外が必要
2. この秤の残量表示は長期的に **10%** 前後（915 件のキャプチャの最頻値）で、故障ではない

### 6.4 履歴パケット（`0x01`）

接続に成功すると秤は「未同期」の旧記録をすべて自動で送ってくる。1 件も 20 バイトだ：

```
時刻    = d[3..6]   （Unix タイムスタンプ、4 バイト、ビッグエンディアン）
体重    = ((d[8]<<16 | d[9]<<8 | d[10]) - 0x680000) / 1000
インピーダンス1 = (d[11]<<8 | d[12])
インピーダンス2 = (d[13]<<8 | d[14])
```

**発火条件**（ここが重要）：

```
「08 時刻合わせ + 01 ユーザー + D0 完全ハンドシェイク」を書き終えると、秤は未同期の記録をすべて自動で送ってくる。
04D8 は必須ではない（送ったほうがより確実）。
```

送り終えると、秤は内部的にそれらの記録を「同期済み」と印付けし、**以後は送ってこない**（新しい測定が生まれるまで）。
秤にもともと記録が無ければ、接続後は静かなままだ——これは正常で、故障ではない。

⚠️ **同じタイムスタンプを 3 回受け取ることがある**（Bluetooth は重複配送する）。必ず重複排除が必要だ。
私たちの実装では `タイムスタンプ_体重` を組み合わせて一意な key とし、それで判定している。

### 6.5 「今どの段階まで測れているか」をどう判断するか

```
0x02 を受信                              → 完了（確定インピーダンスあり）
0x00 または 0x80 を受信、かつ d[11] >= 100 → インピーダンス測定中
その他                                    → 計量中
```

**インピーダンスについて最も重要な一言**：

> インピーダンスは**物理的な条件**だけで決まる。両足を裸足で 4 つの電極に当てて人体回路ができたときだけ値が出る。
> 片足、靴下、足裏が乾きすぎ、のいずれかならインピーダンスは必ず **0** で、どんなコマンドでも値を生み出せない。[A/B 対照実測]
>
> ネット上の「`04 D6` を送ればインピーダンス測定が始まる」は**誤り**——それはリアルタイムパケットが増えるだけ（26→77 件）。
> 本当のインピーダンス値は `0x02` 確定パケットの第 4〜8 バイトにしか現れない。

## 7. 1 回の完全な測定は、最初から最後までどう進むか

```
タイムライン
│
├─ ユーザーが秤に乗る、秤の画面が点灯
│
├─ 秤：アドバタイジングで「私は AFU-WL-TZ-A1」と叫ぶ              —— 999ms ごと、止まらずに
│
├─ スマホ：見つける → MAC で接続 → FFB2 を購読
│
├─ スマホ：8 つのコマンドを順に送る（各 400ms 間隔）              —— 約 3.2 秒
│    08 時刻合わせ → 01 ユーザー → 02 スロット → D0 ハンドシェイク
│    → 06 照会 → 04D6 → 04D8 → 04D8
│
├─ 秤：0x00 リアルタイムパケットを送り始める（100〜150ms ごと）   —— 数字が跳ねる
├─ 秤：体重が安定 → 0x80 安定パケットを送る
├─ 秤：インピーダンス測定へ移行 → d[11] >= 100
├─ 秤：測定完了 → 0x02 確定パケットを繰り返し送る（約 6 秒）      —— 確定インピーダンス付き
│
├─ スマホ：確定パケットを解析 → 体重 + 体脂肪を算出 → DB に保存
│
├─ 秤：未同期の旧記録がまだあれば → 0x01 履歴パケットを送る
│         送り終えたら秤内部で「同期済み」と印付け
│
└─ 終了（秤はしばらくして自分でスリープする）
```

**なぜ確定パケットは 6 秒間も繰り返し送られるのか**？Bluetooth はパケットを落とすことがあるので、複数回送ってスマホが確実に受け取れるようにするためだ。
スマホ側は 1 回受け取れば止めてよい。

## 8. 私たちが実際に踏んだ落とし穴

この節は本文書で最も価値のある部分だ——**ネット上の 4 本のリバースドキュメントはどれも触れていない**。

### 落とし穴 1 · キャラクタリスティックへの書き込みは「書留」モードしか使えない

`FFB1` は応答付き書き込みしか受け付けない。応答なしモードでは **100% 例外が投げられる**。
（vitaloop は Kotlin の既定が応答付きなので踏んでいない。一部の JS/Dart ライブラリは既定で応答なし。）

### 落とし穴 2 · Android 12 の「denylist」がアドバタイジングを黙って飲み込む

スキャン権限に `neverForLocation` フラグを付けると、この秤のアドバタイジングがシステムに beacon と判定されてフィルタされる。
権限は全部与え、Bluetooth も有効なのにスキャンできず、logcat には `Skipping data matching denylist` の一行だけが出る。

### 落とし穴 3 · MIUI では Bluetooth ライブラリによって速度が 400 倍違う

同じスマホ、同じ秤で：

| ライブラリ | スキャン所要時間 |
| --- | --- |
| `flutter_blue_plus` | **1 秒以内** |
| `react-native-ble-plx` | **約 7 分** |

これは**ライブラリのラッパ層の違い**で、権限とは関係ない。これが私たちが最終的に RN から Flutter へ書き換えた直接の理由でもある。

### 落とし穴 4 · UUID でスキャンフィルタすると秤を取りこぼす

`startScan([ffb0 の UUID])` は MIUI で 4 分経っても結果が出ない。全量スキャン + コールバック内で自分で絞れば、すぐ出る。

### 落とし穴 5 · 接続直後に状態が「偽の切断」になる

GATT を確立したその瞬間、接続状態が一瞬 `disconnected` と誤報される。
「切断したら再接続」というタイマーをそのまま仕掛けると、**ハンドシェイクが 2 回**走る——秤はこれを新しい同期セッションとみなし、履歴をもう一度送ってくる。

直し方：再接続の前に `isConnected` を再確認し、「接続中」を表す排他ロックを入れる。

### 落とし穴 6 · 「体重が変わったか」のしきい値を大きくしすぎない

最新の体重をメンバープロフィールに反映したいので、「値が変わったか」を判定する必要がある。

| しきい値 | 結果 |
| --- | --- |
| 1 kg | 0.1kg 増えても「変わっていない」と見なされ、永久に更新されない |
| 0.05 kg | 浮動小数点の精度問題：55.85 − 55.80 は 0.0499… になるので、これも弾かれる |
| **0.001 kg** | ✅ 最終的にこれを採用 |

### 落とし穴 7 · 男女でまったく違う体脂肪の式を使う必要がある

```
男性 = Deurenberg の式：1.10×BMI + 0.23×年齢 − 11.22   （インピーダンスは使わない！）
女性 = Segal の式：インピーダンスが必要。2 組のインピーダンスを (i1+i2)×0.675 で合成する
```

**もう 1 つ知っておくべきこと**：秤の画面に出る体脂肪率と、App が計算した値は**0 点数ポイントずれる**。
秤はメーカーの独自アルゴリズム（非公開）を使い、App は上記の公開論文にある式を使うからだ。

両者で **BMI は常に一致する**（BMI は体重と身長だけを見るので、アルゴリズムの分岐が入り込む余地がない）。

性別を間違えると、結果が 2 倍近く違ってくる。例を挙げる（55.75kg / 163cm / 24 歳 / インピーダンス 430+387）：

| どの式を使うか | 算出される体脂肪率 |
| --- | --- |
| 男性の式 | 17.4% |
| 女性の式 | 22.2% |

### 落とし穴 8 · 秤に「前回のユーザー設定」が残っている

秤は前回書き込まれたユーザースロットを保持する。App 側のプロフィールを変えても秤の中が古いままだと、
秤の画面に出る体脂肪は明らかにおかしくなる。これが私たちが接続のたびに `02` コマンドを送って上書きしている理由だ。

### 落とし穴 9 · バッテリー残量は 77% ではなく 10%

| 出どころ | 読み値 | 真偽 |
| --- | --- | --- |
| 標準バッテリーサービス `0x2A19` | 77% | ❌ ゴミ値（このサービスはそもそも存在しない）|
| リアルタイムパケット `d[11] & 0x7F` | 10% | ✅ 真値（915 件のキャプチャの最頻値）|

### 落とし穴 10 · 秤には「記録の削除」機能が無い

公式の書き込みコマンド 29 件を全部調べたが、**削除／クリアの命令は 1 つも無かった**。

つまり：秤がとある記録を「同期済み」と印付けた時点で、どの App もそれを取得できなくなる。
**App 側で保存し損ねる＝永久消失**。だから接続中は絶対に途中でプロセスを殺してはいけない。

## 9. ネット上の 4 本のリバースドキュメントとの相違

私たちは 5 つのオープンソースプロジェクトを参考にしたが、**その通りにやると事故る**箇所が少なくない。
この節は実測結論とドキュメントの記述との食い違いを並べ、後から来る人が回り道をしないようにするためのものだ。

### 9.1 ドキュメントの記述 vs 実測結論

| # | ドキュメントの記述 | 実測結果 | 証拠 |
| --- | --- | --- | --- |
| 1 | [AF] 体重は完全な 32 ビットで、`& 0x3FFFF` で段階分けする | リアルタイム／安定パケットは `((d[3]-0x68)×65536+d[4]×256+d[5])/1000`；**確定パケットの体重は d[10:13]** で、2 か所で位置が違う | 55.75kg の全経路照合 |
| 2 | [AF] 秤はスリープ中にアドバタイジングせず、踏んで点灯させる必要がある | 本機は**画面が点いていなくてもアドバタイジングしている**（999ms）。nRF では 2 秒で捕捉、検証台では 84ms | nRF + 通信ログ |
| 3 | [AF] プロフィールパケットを 15 秒ごとに再送するのでハートビートが必要 | **ハートビートは不要**。送らなくても安定してインピーダンスが出る | ハートビート無しで実測正常 |
| 4 | [VA] ハンドシェイク時の weight/target は 0 を入れる | **実値**を入れたほうがよく、秤内のスロットとプロフィールが一致する | 実測ログ |
| 5 | [VA] `D0` ハンドシェイクを 1 回送れば十分 | `01` ユーザーコマンドを伴わないと**インピーダンスが発火しない**。8 件の全シーケンスが最も安定 | 前後比較 |
| 6 | [WT] ServiceData の payload には `AC27` の接頭辞が付く | payload = **MAC 6 バイト（逆順）+ 01** で、接頭辞は無い | 生バイトの照合 |
| 7 | [WT] `D6` コマンドがインピーダンスの源 | `D6` はリアルタイムパケットを増やすだけ（26→77 件）で、**確定インピーダンスは `0x02` パケットの d[4:8]** にある | A/B 対照 |
| 8 | [WT/HCI] チェックサム = 本文の合計 | 正確には **`sum(frame[2..18]) & 0xFF`**（**尾部 [18] を含む**）| バイト単位の照合 |

### 9.2 4 本のドキュメントがどれも書いておらず、私たちが自分で見つけたこと

1. `FFB1` は**応答付き書き込みしか受け付けない**（詳細は落とし穴 1）
2. Android 12 の `neverForLocation` によりアドバタイジングが denylist でフィルタされる（落とし穴 2）
3. MIUI では 2 種類の Bluetooth ライブラリで速度が 400 倍違う（落とし穴 3）
4. UUID の事前フィルタでは秤を取りこぼす（落とし穴 4）
5. 接続瞬間の状態ゆらぎでハンドシェイクが 2 回走る（落とし穴 5）
6. プロフィールへの反映しきい値は 0.001kg まで小さくする必要がある（落とし穴 6）
7. 男女で BIA の式がまったく違う（落とし穴 7）
8. `02` コマンドの本当の意味は「ユーザースロットを 2 組、各 7 バイト書き込む」こと
9. バッテリー残量の真値は `d[11]` の下位 7 ビットにあり、この秤に `0x2A19` サービスは無い（落とし穴 9）
10. 「同期済み」の印付けは**どの** App にも作用し、削除コマンドが無いことと相まって、保存し損ねれば永久消失（落とし穴 10）

### 9.3 公式 Ant Afu アプリとの意図的な相違

| 公式のやり方 | 私たちのやり方 | 理由 |
| --- | --- | --- |
| 紐付け解除時だけ `02` を送る | 接続のたびに送る（実験的）| 秤に残った古いユーザー設定を上書きする（111cm に張り付いた事例あり）|
| 15 秒ごとにプロフィールパケットを再送（ハートビート）| 送らない | 実測で不要、省電力 |
| `04D8` を 1 回 | 2 回 | 保険。副作用は観測されていない |
| iOS クライアント | Android / Flutter | スキャン戦略が違う（落とし穴 3、落とし穴 4 参照）|

### 9.4 まだ検証していない問題

- [ ] 接続のたびに `02` を送ることの長期的な副作用（履歴が繰り返し再送されるのが見えたら「紐付け解除時のみ」に戻す）
- [ ] `deviceType` に `0x29` を送ることが一部ファームウェアで必須か（vitaloop は 0x29 でも動作する）
- [ ] 体脂肪率と秤画面の 0.4 ポイントの差が、体重に対して一定なのか
- [ ] 15 秒ハートビートが超長時間接続（10 分超）で必要か

## 10. 自分でどうデバッグするか

### 10.1 App 内の通信ログを開く

ログの入口は既定で隠してある（イースターエッグ）：

> **設定 → バージョン情報 → バージョン番号を 7 回連打**

解錠すると測定ページ右上に「通信 N」ボタンが現れ、送受信した 1 件ずつの生バイトを見られる。

### 10.2 ログファイルは自動で書き出される

接続中は 3 秒ごとに書き込む（切断時にもう一度強制書き込み）：

```
/storage/emulated/0/Android/data/com.aiyue.afu_scale/files/comm_latest.txt
```

```bash
adb pull /storage/emulated/0/Android/data/com.aiyue.afu_scale/files/comm_latest.txt
```

形式：`時刻 方向(→送信 / ←受信) 生 20 バイト [コマンド名またはパケット種別]`

### 10.3 システム側のキーワード

| 症状 | logcat のキーワード |
| --- | --- |
| スキャンがシステムにフィルタされる | `Skipping data matching denylist` |
| スキャン過程の計測点 | `SCAN_STEP` |
| 書き込み失敗 | `PlatformException` + `not supported` |

### 10.4 nRF Connect でクロスチェック

自作のプログラムの挙動がおかしいときは、まず **nRF Connect**（スマホ用の汎用 BLE デバッグツール）で手動接続し、
正常にデータが受け取れるかを確かめる。nRF でもだめなら、物理／環境の問題だ（踏んで点灯させていない、離れすぎ、残量低下）。

## 付：自分で実装したい人向けの早見表

```
1. スキャン：全量スキャンし、コールバック内で「名前に AFU-WL / ServiceData が 27AC / サービスに FFB0」で絞る
2. MAC を取得：ServiceData の 6 バイトを逆順に読む
3. 接続 → サービス FFB0 を取得
4. FFB2 の通知を購読（setNotifyValue(true)）
5. FFB1 に 8 つのコマンドを書く。各 400ms 間隔、すべて「応答付き」モード
6. FFB2 のコールバックを聞き、[2] でパケット種別を判定
7. 0x02 パケット：体重は d[10:13]、インピーダンスは d[4:8]。どちらもオフセットを引いてから 1000 で割る
8. 0x02 を受け取ったら終わり、DB に保存
```

**最も事故りやすい 3 か所**：書き込みモード（応答付き必須）、チェックサムの範囲（[18] を含む）、体重のオフセット（`0x68` vs `0x680000`）。
