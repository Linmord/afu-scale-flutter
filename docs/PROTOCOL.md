## 0. 一句话概括我们在干什么

这台秤本质是一台**会说话的电子秤**。它和手机之间：

1. 秤不停地在空气里"广播"自己的名字和身份（像店铺挂着招牌）
2. 手机收到招牌后连上去，拿到两个"信箱"：一个用来发，一个用来收
3. 手机按固定顺序塞进去 8 封格式统一的小纸条（**握手**）
4. 秤开始往收信箱里丢数据包，手机逐字节拆开、算出体重和体脂

听起来简单，但**每一层都有坑**——常见协议文档只写"应该怎么做"，
这篇把"实际做的时候会怎么翻车"也写进去了。

## 1. 先认识几个词

蓝牙里有一堆术语，第一次看会懵。用**快递柜**打个比方：

| 术语 | 快递柜类比 | 实际含义 |
| --- | --- | --- |
| **广播（Advertising）** | 柜子上贴的招租广告 | 设备不用连接，也能一直往外喊"我在这，我叫什么" |
| **扫描（Scan）** | 物业拿着地图挨个看广告 | 手机不连接，只"听"空气里谁在喊 |
| **GATT** | 快递柜的整套管理制度 | 蓝牙低功耗（BLE）传数据的标准规则集 |
| **服务（Service）** | 一个柜子，比如"3 号柜" | 一组功能的集合，用 UUID 编号 |
| **特征值（Characteristic）** | 柜子里的一个小格子 | 真正存/取数据的地方，也有自己的 UUID |
| **写入（Write）** | 你往里塞快递 | 手机 → 设备 发数据 |
| **通知（Notify）** | 柜子满了主动推送微信提醒 | 设备 → 手机 主动发数据（不用手机问）|
| **UUID** | 柜子的编号，如 `0000ffb0-...` | 一串 128 位（16 字节）的编号，标识某个服务/格子 |
| **MAC 地址** | 身份证号 | 蓝牙设备唯一的硬件地址，如 `AA:BB:CC:DD:EE:FF` |
| **字节序（大端/小端）** | 数字 1234 是"1 先写还是 4 先写" | 多个字节拼一个数字时，高位在前还是低位在前 |

**为什么要知道字节序**：后面你会发现，同样是体重，秤在两种包里一个用**大端**一个用**小端**，
搞反了就会算出离谱的数字（比如把 55.75kg 读成 14 吨）。

## 2. 第一步：在空气里找到它（扫描）

### 2.1 秤都"喊"了什么

秤的广播里带着这几样东西（我们用 nRF Connect 和系统日志核对过）：

| 内容 | 值 |
| --- | --- |
| 广播名 | `AFU-WL-TZ-A1` |
| 服务 UUID | `0xFFB0`、`0x1530` |
| 厂商数据 | 厂商 ID `0x27AC` |
| **ServiceData** | `0x27AC` + **真实 MAC（6 字节，倒序）+ 01** |
| 广播间隔 | 999 毫秒 |

**这里有个反直觉的点**：广播里出现的那个蓝牙地址（RemoteID），
**不一定是秤真实的 MAC**。真实值藏在 ServiceData 里，而且是**倒着放的**。

```
ServiceData 原始字节：  FF EE DD CC BB AA 01
                        └──── 6 字节倒序 ────┘ └(固定 01)
倒过来读：              AA:BB:CC:DD:EE:FF   ← 这才是真 MAC
```

> 我们第一次解析时看漏了"倒序"，结果 MAC 差了一位，怎么也连不上。[WT/实测]

### 2.2 手机怎么认出它

三个条件**任意命中一个**就算：

1. 广播名里含 `AFU-WL`
2. ServiceData 里的 UUID 是 `0x27AC`
3. 广播的服务列表含 `0xFFB0`

### 2.3 两个必须知道的坑

**坑一：不要用 UUID 做前置过滤**

很多教程教你 `startScan([ffb0的UUID])`，只扫带这个服务的设备——在这台秤上**会漏**。
实测 MIUI 上这样做 4 分钟都扫不到；改成"全扫 + 在回调里自己筛"，1 秒出结果。[实测]

**坑二：别加 `neverForLocation` 标志**

Android 12 以后申请蓝牙扫描权限时，如果带上"这个扫描不用于定位"的标志，
系统会**静默过滤掉**某些类型的广播（这台秤的广播正好被判定成 beacon）。
现象是：权限都给了、蓝牙也开了，就是扫不到。

logcat 里能看到：`Skipping data matching denylist`。去掉这个标志就好。[实测]

## 3. 第二步：连上去，拿到两个"信箱"

连接用第 2 步解出来的**真实 MAC**。连上之后，你会看到一个服务：

```
服务 0000ffb0-0000-1000-8000-00805f9b34fb
  ├── 特征值 FFB1  ← 手机往这里"写"命令
  └── 特征值 FFB2  ← 秤往这里"发"数据（需要先订阅通知）
```

### 3.1 写信箱 FFB1：只能寄"挂号信"

BLE 写入有两种模式：

| 模式 | 通俗解释 | 这台秤支持吗 |
| --- | --- | --- |
| **WRITE**（带响应） | 挂号信，会告诉你"收到了" | ✅ 必须用这个 |
| WRITE_NO_RESPONSE（不带响应） | 往门缝里塞纸条，不管收没收到 | ❌ **100% 报错** |

> 这是最容易卡住的地方：某些 BLE 库默认用"不带响应"模式（性能更好），
> 在这台秤上每次都会抛异常。我们用 8 次写入验证过，全都失败。[实测]

### 3.2 收信箱 FFB2：要先"订阅"

手机不能干等着秤发数据，得先调用一次 `setNotifyValue(true)`（订阅）。
订阅之后，秤每发一条，手机的"回调函数"就会被调用一次，参数是 20 个字节。

```dart
// flutter_blue_plus 的做法
await char.setNotifyValue(true);
char.onValueReceived.listen((data) {
  // data 是 Uint8List，长度 20
});
```

### 3.3 顺便能读到的设备信息

秤还暴露了一个标准信息服务 `0x180A`（Device Information），能读到：

| 字段 | 值 |
| --- | --- |
| 制造商 | ICOMON |
| 型号 | FG2313UWB-D |
| 固件版本 | 1.2.3 |
| 软件版本 | 1.3.0 |

⚠️ **别去读电量特征值 `0x2A19`**——这台秤根本没有这个标准服务，
读出来的是垃圾值（比如 77%），真电量藏在数据包里的另一个位置（见 §6.3）。[实测]

## 4. 第三步：搞懂"信封"的格式

手机和秤之间所有消息都是**固定 20 字节**，一个字节不多一个字节不少。
你可以把它想成一个标准的信封，上面印着几个固定的格子：

```
字节位置：  [0]  [1]   [2] [3] [4] ... [17]   [18]   [19]
          ┌────┬────┬──────────────────────┬──────┬──────┐
内容：    │ AC │ 类型│      正   文           │ 尾部 │ 校验 │
          │    │     │     （16 字节）        │(命令)│ 和   │
          └────┴────┴──────────────────────┴──────┴──────┘
```

| 位置 | 叫什么 | 说明 |
| --- | --- | --- |
| `[0]` | 起始标志 | 固定 `0xAC`，相当于信封上的"航空邮件"戳 |
| `[1]` | 设备类型 | 手机发 `0x27`，秤回 `0x29`（双方各报各的"身份"）|
| `[2..17]` | 正文 | 16 字节，真正的命令和数据放这里 |
| `[18]` | 尾部 | 命令编号，帮助区分这是哪个命令 |
| `[19]` | 校验和 | 防止传输过程中数据被改坏 |

### 4.1 校验和是什么

想象你寄一封信，在信封封口处写一个数字：**"里面所有字的笔画数加起来"**。
收信人拆开后重新数一遍，如果对不上，说明信在路上被弄坏了。

这里的规则是：

```
校验和 = (第2到第18字节全部相加) & 0xFF
```

**`& 0xFF` 是什么意思**？

一个字节最大能存 255。相加的结果可能远超 255（比如 2000），
`& 0xFF` 就是"**只保留最后 8 个二进制位**"，等价于"对 256 取余数"。

```
举例：相加得到 2000
2000 = 二进制 11111010000   （11 位）
只看后 8 位 → 11010000 = 208
所以校验和写 208（0xD0）
```

> ⚠️ 注意范围是 `[2..18]`——**包含尾部 `[18]`，不包含自己 `[19]`**。
> 网上有文档说"只对正文求和"，照做会一直失败。[实测逐字节核对]

### 4.2 正文超过 16 字节会被砍掉

拼帧函数里有个截断：第 2 到第 17 共 16 格，多出来的直接丢弃。
所以**单条命令的正文最多 16 字节**，塞不下就得分包。

## 5. 第四步：按顺序发 8 条命令（握手）

连上之后**不能直接问数据**，得先"报到"。秤要先认识你是谁，才肯干活。

顺序固定，每条间隔 **400 毫秒**（发太快对方处理不过来会丢）。

| # | 命令 | 作用 | 正文（16 字节）|
| --- | --- | --- | --- |
| 1 | `08` 对时 | 告诉秤"现在几点" | `08` + Unix 秒（4 字节）+ 时区 |
| 2 | `01` 用户 | 告诉秤"我是谁" | `01 00 01` + 身高 + 体重（2 字节×100）+ 年龄 + 性别 |
| 3 | `02` 槽位 | 覆盖秤里存的用户配置 | 两组各 7 字节（槽位1 / 槽位2）|
| 4 | `D0` 完整握手 | 一次性把所有信息再报一遍 | 时间 + 时区 + 单位 + 槽位 + 身高 + 体重 + 年龄 + 性别 + 目标 + `03 00` |
| 5 | `06` 查询 | 问配置 | `06` |
| 6 | `04 D6` | 提高实时包频率 | `04 D6` |
| 7 | `04 D8` | 请求历史记录（第一次）| `04 D8` |
| 8 | `04 D8` | 请求历史记录（第二次）| `04 D8` |

### 5.1 几个容易搞错的细节

**① 时区怎么算**

```
utcQuarters = (UTC偏移分钟数 ÷ 15) & 0xFF
```

为什么按 15 分钟？因为世界上有些时区是 UTC+5:30、UTC+5:45 这种半小时/一刻钟的偏移，
用 15 分钟当最小单位刚好能表示全部时区。中国是 UTC+8 → 480 分钟 → 480÷15 = **32**。

**② 性别只有两个值**

```
男 = 1    女 = 2
```

⚠️ 这不是编程里常见的"0/1"，是**1 和 2**。写错会导致体脂公式选错，结果差一倍。

**③ 体重要乘 100 存**

体重用 2 个字节（最大 65535）存，单位是"百分之一千克"。
所以 55.75kg 存成 `5575` = 十六进制 `0x16 0b`。

**④ 身高只存整数**

身高只占 1 个字节（最大 255cm），所以 165.4cm 会变成 **165**。

**⑤ 这些数值从哪来**

```
体重 = 成员档案里的体重 → 最近一次测量记录 → 都没有就用 60kg 兜底
目标体重 = 用户设定的 → 没设就用"参考体重 × 0.75"
```

### 5.2 第 3 条 `02` 命令的特殊性

官方的蚂蚁 App **只在"解绑设备"时**发这条命令，作用是清掉秤里存的用户槽位。

我们改成**每次连接都发**——因为遇到过秤里残留旧配置（身高卡在 111cm，怎么都改不掉），
重发这条能覆盖掉。属于实验性做法，副作用见 §8。[HCI]

## 6. 第五步：读懂秤回的话

秤发来的包也是 20 字节，`[0]` 是 `0xAC` 但 `[1]` 变成 `0x29`。
真正的"这是哪种包"藏在 `[2]` 里：

| `[2]` 的值 | 包类型 | 什么时候出现 |
| --- | --- | --- |
| `0x00` | 实时包 | 测量过程中，每 100~150ms 一条 |
| `0x80` | 稳定包 | 体重稳定下来了 |
| `0x02` | **锁定包** | 测量完成，带最终阻抗（最重要）|
| `0x01` | 历史包 | 连接后秤主动推未同步的旧记录 |
| `0x06` | 配置块 | 应答 `06` 查询，连推 5 包 |

### 6.1 体重怎么从 3 个字节算出来

这是全篇最需要理解的地方。先看实时包用的公式（**小端式写法**）：

```
体重(g) = ((d[3] - 0x68) × 65536 + d[4] × 256 + d[5]) ÷ 1000
```

**为什么要乘 65536 和 256？**

因为一个字节只能存 0~255，存不下几百公斤（以克为单位是几十万）。
所以用了**三个字节拼成一个"大数字"**：

```
把三个字节想象成三个旋钮：
  第 1 个旋钮（d[3]）：每转一格 = +65536
  第 2 个旋钮（d[4]）：每转一格 = +256
  第 3 个旋钮（d[5]）：每转一格 = +1

这就像十进制里：百位 ×100、十位 ×10、个位 ×1
只不过这三个"位"是 256 进制，所以权重是 65536 / 256 / 1
```

**`- 0x68` 是干什么的？**

秤的出厂"零点"不是 0，而是 `0x68`（十进制 104）。相当于老式体重秤的指针本来就没对准零，
要先扣掉这个偏移量。

**`÷ 1000`**：因为算出来的单位是克，要换成千克。

### 6.2 锁定包的体重为什么换了位置和写法

锁定包的体重在 **`d[10..12]`**（不是 `d[3..5]`），而且公式变成了：

```
体重(g) = ((d[10]<<16 | d[11]<<8 | d[12]) - 0x680000) ÷ 1000
```

**`<<16`、`|` 是什么？**

`<<16` 就是"左移 16 位"，等价于 **× 65536**；`|` 是"把三段拼起来"。
所以这个公式和上面本质是**同一个算法**，只是写法更"程序员"：

```
写法 A（小学生版）       写法 B（位运算版）
d[10] × 65536            d[10] << 16
d[11] × 256              d[11] << 8
d[12] × 1                d[12]
三者相加                 三者用 | 拼起来
```

⚠️ 但**偏移量不同**：这里是 `0x680000`（不是 `0x68`）。
因为数字整体放大了 65536 倍，偏移也要跟着放大。

**完整实例**（这是我们真机上抓到的一条）：

```
原始包：ac 29 02 00 01 ae 01 83 01 80 68 d9 c6 ...
                             └──┬──┘
                             体重三字节

d[10]=0x68  d[11]=0xD9  d[12]=0xC6
拼起来：0x68d9c6 = 6,871,494
减去偏移：6,871,494 - 0x680000(6,815,744) = 55,750
除以 1000：55,750 ÷ 1000 = 55.75

→ 体重 55.75 kg ✅

同一包里的阻抗：
阻抗1 = (d[4]<<8 | d[5]) = (0x01<<8 | 0xae) = 256 + 174 = 430 Ω
阻抗2 = (d[6]<<8 | d[7]) = (0x01<<8 | 0x83) = 256 + 131 = 387 Ω
```

### 6.3 电量藏在哪

**没有标准电池服务**（§3.3 说过）。真电量在实时包的 `d[11]` 的**低 7 位**：

```
电量 = d[11] & 0x7F
```

`& 0x7F` = "只保留低 7 位"（最高位当作标志位，不算进电量）。

⚠️ **两个陷阱**：
1. 测量过程中 `d[11]` 会变成 `0x64`（=100），这是"测量完成"的状态标志，**不是电量**，要排除
2. 这台秤的电量长期就显示 **10%** 左右（915 条抓包的众数），不是坏了

### 6.4 历史包（`0x01`）

连接成功后秤会自动把所有"没同步过"的旧记录推下来，每条也是 20 字节：

```
时间   = d[3..6]   （Unix 时间戳，4 字节，大端）
体重   = ((d[8]<<16 | d[9]<<8 | d[10]) - 0x680000) / 1000
阻抗1  = (d[11]<<8 | d[12])
阻抗2  = (d[13]<<8 | d[14])
```

**触发条件**（这点很关键）：

```
写完「08 对时 + 01 用户 + D0 完整握手」之后，秤会自动把所有未同步记录推下来，
04D8 不是必需的（发了更保险）。
```

推完之后，秤在内部把这些记录标记成"已同步"，**以后不再推**，直到产生新的测量。
如果秤里本来就没有记录，连接后会一片安静——这是正常的，不是坏了。

⚠️ **同一个时间戳可能收到 3 次**（蓝牙会重复投递），必须去重。
我们的做法是用 `时间戳_体重` 拼成唯一 key 判断。

### 6.5 怎么判断"现在测到哪一步了"

```
收到 0x02                          → 完成（有最终阻抗）
收到 0x00 或 0x80，且 d[11] >= 100 → 正在测阻抗
其他                                → 正在称重
```

**关于阻抗最重要的一句**：

> 阻抗只由**物理条件**决定。双脚赤脚踩住四个电极片形成人体回路才有值；
> 单脚、穿袜子、脚底太干，阻抗一定是 **0**，任何命令都变不出来的。[A/B 对照实测]
>
> 网上说"发 `04 D6` 就能开启阻抗测量"是**错的**——那只让实时包变多（26→77 条）。
> 真正的阻抗数值只出现在 `0x02` 锁定包的第 4~8 字节。

## 7. 一次完整测量，从头到尾是什么样

```
时间轴
│
├─ 用户踩上秤，秤屏幕亮起
│
├─ 秤：广播里喊"我是 AFU-WL-TZ-A1"           —— 999ms 一次，不停喊
│
├─ 手机：扫到它 → 按 MAC 连接 → 订阅 FFB2
│
├─ 手机：按顺序发 8 条命令（每条隔 400ms）    —— 约 3.2 秒
│    08 对时 → 01 用户 → 02 槽位 → D0 握手
│    → 06 查询 → 04D6 → 04D8 → 04D8
│
├─ 秤：开始推 0x00 实时包（每 100~150ms）      —— 数字在跳
├─ 秤：体重稳定 → 推 0x80 稳定包
├─ 秤：进入阻抗测量 → d[11] >= 100
├─ 秤：测量完成 → 循环推 0x02 锁定包（约 6 秒）—— 带最终阻抗
│
├─ 手机：解析锁定包 → 算出体重 + 体脂 → 存库
│
├─ 秤：如果还有没同步的旧记录 → 推 0x01 历史包
│         推完在秤内部标记"已同步"
│
└─ 结束（秤过一会儿自己休眠）
```

**为什么锁定包要循环推 6 秒**？因为蓝牙可能丢包，多推几次保证手机一定收到。
手机只要收到一次就可以停了。

## 8. 我们真踩过的坑

这一节是本文档最有价值的部分——**网上四份逆向文档都没提到**。

### 坑 1 · 写特征值只能用"挂号信"模式

`FFB1` 只支持带响应的写入。用不带响应模式，**100% 抛异常**。
（vitaloop 用 Kotlin 默认就是带响应，所以没踩到；某些 JS/Dart 库默认不带。）

### 坑 2 · Android 12 的"denylist"会静默吃掉广播

扫描权限带 `neverForLocation` 标志时，这台秤的广播被系统判定为 beacon 并过滤掉。
权限全给了、蓝牙也开着，就是扫不到，logcat 里只有一句 `Skipping data matching denylist`。

### 坑 3 · MIUI 上不同蓝牙库速度差 400 倍

同一台手机、同一台秤：

| 库 | 扫描耗时 |
| --- | --- |
| `flutter_blue_plus` | **1 秒内** |
| `react-native-ble-plx` | **约 7 分钟** |

这是**库的封装层差异**，跟权限无关。这也是我们最终从 RN 改写成 Flutter 的直接原因。

### 坑 4 · 用 UUID 做扫描过滤会漏掉秤

`startScan([ffb0的UUID])` 在 MIUI 上 4 分钟无结果；全量扫描 + 回调里自己筛，秒出。

### 坑 5 · 刚连上时状态会"假断开"

GATT 建立的那一瞬间，连接状态会短暂误报 `disconnected`。
如果直接挂个"断开就重连"的定时器，就会**握手两遍**——秤会当成新的同步会话，把历史重推一遍。

修法：重连前先复查 `isConnected`，并加一个"正在连接中"的并发锁。

### 坑 6 · 判"体重变了没"的阈值不能太大

我们想把最新体重回填到成员档案，需要判断"值有没有变"。

| 阈值 | 后果 |
| --- | --- |
| 1 kg | 涨了 0.1kg 视为"没变"，永远不更新 |
| 0.05 kg | 浮点数精度问题：55.85 − 55.80 算出来是 0.0499…，还是被挡 |
| **0.001 kg** | ✅ 最终采用 |

### 坑 7 · 男女要用完全不同的体脂公式

```
男性 = Deurenberg 公式：1.10×BMI + 0.23×年龄 − 11.22   （阻抗不参与！）
女性 = Segal 公式：需要阻抗，把两组阻抗合成 (i1+i2)×0.675
```

**还有一个要知道的**：秤自己屏幕上显示的体脂率，和 App 算出来的**会差零点几个百分点**。
因为秤用的是厂商私有算法（不公开），App 用的是上面这些公开论文里的公式。

两者**BMI 永远一致**（BMI 只看体重和身高，没有算法分歧的地方）。

套错性别，结果差将近一倍。举个例子（55.75kg / 163cm / 24岁 / 阻抗 430+387）：

| 用哪个公式 | 算出的体脂率 |
| --- | --- |
| 男性公式 | 17.4% |
| 女性公式 | 22.2% |

### 坑 8 · 秤里存着"上一次的用户配置"

秤会保留上次写入的用户槽位。如果 App 里的档案改了但秤里还是旧的，
秤屏显示的体脂会明显不对。这也是我们每次连接都发 `02` 命令覆盖的原因。

### 坑 9 · 电量不是 77%，是 10%

| 来源 | 读数 | 真伪 |
| --- | --- | --- |
| 标准电池服务 `0x2A19` | 77% | ❌ 垃圾值（这服务根本不存在）|
| 实时包 `d[11] & 0x7F` | 10% | ✅ 真值（915 条抓包众数）|

### 坑 10 · 秤没有"删除记录"这个功能

官方 29 条写命令我们全查过了，**没有任何删除/清空指令**。

这意味着：一旦秤把某条记录标记成"已同步"，任何 App 都拿不到它了。
**App 漏存 = 永久丢失**。所以连接期间千万别中途杀进程。

## 9. 和网上四份逆向文档的差异

我们参考了五个开源项目，但**照着做会翻车**的地方不少。
这节列的是实测结论与文档说法的出入，方便后来人少走弯路。

### 9.1 文档说法 vs 实测结论

| # | 文档怎么说 | 实测是什么 | 证据 |
| --- | --- | --- | --- |
| 1 | [AF] 体重是完整 32 位，用 `& 0x3FFFF` 分档 | 实时/稳定包用 `((d[3]-0x68)×65536+d[4]×256+d[5])/1000`；**锁定包体重在 d[10:13]**，两处位置不同 | 55.75kg 全链路核对 |
| 2 | [AF] 秤休眠时不广播，必须踩亮 | 本秤**未亮屏也在广播**（999ms），nRF 2 秒扫到，验证台 84ms | nRF + 通讯日志 |
| 3 | [AF] 资料包每 15 秒重发，需要心跳 | **心跳非必需**，不发也能稳定出阻抗 | 无心跳实测正常 |
| 4 | [VA] 握手时 weight/target 填 0 | 填**真实值**更好，秤内槽位与档案一致 | 实测日志 |
| 5 | [VA] 只发一条 `D0` 握手就够 | 不带 `01` 用户命令时**阻抗不触发**，8 条全序列最稳 | 前后对比 |
| 6 | [WT] ServiceData 的 payload 带 `AC27` 前缀 | payload = **MAC 6 字节（倒序）+ 01**，没有前缀 | 原始字节核对 |
| 7 | [WT] `D6` 命令是阻抗来源 | `D6` 只让实时包变多（26→77 条），**最终阻抗在 `0x02` 包 d[4:8]** | A/B 对照 |
| 8 | [WT/HCI] 校验和 = 正文求和 | 精确为 **`sum(frame[2..18]) & 0xFF`**（**含尾部 [18]**）| 逐字节核对 |

### 9.2 四份文档都没写、我们自己发现的

1. `FFB1` **只支持带响应写入**（详见坑 1）
2. Android 12 的 `neverForLocation` 会导致广播被 denylist 过滤（坑 2）
3. MIUI 上两种蓝牙库速度差 400 倍（坑 3）
4. UUID 前置过滤会漏秤（坑 4）
5. 连接瞬间状态抖动会导致双握手（坑 5）
6. 档案回填阈值必须小到 0.001kg（坑 6）
7. 男女 BIA 公式完全不同（坑 7）
8. `02` 命令的真实语义是"写两组用户槽位，每组 7 字节"
9. 电量真值在 `d[11]` 低 7 位，且这秤没有 `0x2A19` 服务（坑 9）
10. "已同步"标记对**任何** App 都生效，加上没有删除命令 = 漏存即永久丢（坑 10）

### 9.3 和官方蚂蚁 App 的有意差异

| 官方怎么做 | 我们怎么做 | 为什么 |
| --- | --- | --- |
| 只在解绑时发 `02` | 每次连接都发（实验性）| 覆盖秤里残留的旧用户配置（曾卡在 111cm）|
| 每 15 秒重发资料包（心跳）| 不发 | 实测非必需，省电 |
| `04D8` 发一次 | 发两次 | 保险，没观察到副作用 |
| iOS 客户端 | Android / Flutter | 扫描策略不同（见坑 3、坑 4）|

### 9.4 还没验证的问题

- [ ] 每次连接都发 `02` 的长期副作用（如果发现历史被反复重推，改回"仅解绑时发"）
- [ ] `deviceType` 发 `0x29` 是否在部分固件上必需（vitaloop 用 0x29 也能工作）
- [ ] 体脂率与秤屏那 0.4 个百分点差异是否随体重恒定
- [ ] 15 秒心跳在超长连接（>10 分钟）下是否必要

## 10. 自己怎么调试

### 10.1 打开 App 里的通讯日志

日志入口默认藏着（彩蛋）：

> **设置 → 关于 → 连点版本号 7 次**

解锁后测量页右上角出现「通讯 N」按钮，能看到每一条收发的原始字节。

### 10.2 日志文件自动落盘

连接期间每 3 秒写一次（断开时再强制写一次）：

```
/storage/emulated/0/Android/data/com.aiyue.afu_scale/files/comm_latest.txt
```

```bash
adb pull /storage/emulated/0/Android/data/com.aiyue.afu_scale/files/comm_latest.txt
```

格式：`时间 方向(→发出 / ←收到) 原始20字节 [命令名或包类型]`

### 10.3 系统层面的关键字

| 现象 | logcat 关键字 |
| --- | --- |
| 扫描被系统过滤 | `Skipping data matching denylist` |
| 扫描过程打点 | `SCAN_STEP` |
| 写入失败 | `PlatformException` + `not supported` |

### 10.4 用 nRF Connect 交叉验证

自己写的程序行为诡异时，先用 **nRF Connect**（手机上的通用 BLE 调试工具）手动连一次，
看能不能正常收到数据。如果 nRF 也不行，说明是物理/环境问题（没踩亮、离太远、电量低）。

## 附：给"想自己实现"的人一张速查表

```
1. 扫描：全量扫，回调里按「名字含 AFU-WL / ServiceData 是 27AC / 服务含 FFB0」筛
2. 取 MAC：ServiceData 里 6 字节倒序
3. 连接 → 拿到服务 FFB0
4. 订阅 FFB2 的通知（setNotifyValue(true)）
5. 往 FFB1 写 8 条命令，每条隔 400ms，全部用「带响应」模式
6. 听 FFB2 的回调，按 [2] 判断包类型
7. 0x02 包：体重在 d[10:13]，阻抗在 d[4:8]，都要减偏移再除 1000
8. 收到 0x02 就完事了，存库
```

**最容易翻车的三处**：写入模式（必须带响应）、校验和范围（含 [18]）、体重偏移量（`0x68` vs `0x680000`）。
